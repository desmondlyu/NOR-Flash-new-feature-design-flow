# NOR Flash DV Design

產出供工程師審查測試構想的驗證計畫書。完成標準是讀者能理解「為什麼測、怎麼測、看什麼、如何判斷」，不要求程式實作細節。本 skill 不產生測試程式，也不要求接續 Writer 或任何特定設備的 skill。

方法來源：[pstack /statechart](https://github.com/cursor/plugins/tree/main/pstack/skills/statechart)。

借用其「讓人審查產品狀態、沿操作路徑找出違反規則的可能性、再以實際行為核對」的方法。本 skill 以 HTML 呈現文件推演，不預設執行形式驗證或窮舉狀態，也不宣稱已證明產品正確。工程師審查 AI 對規格與設計意圖的理解；產出期間不增加逐階段核可。

開始撰寫計畫前，先依文末「用詞與文字」取得並讀取兩份文字編輯 skill；未安裝時仍須嘗試原 repo 讀取與搜尋備援。

## 1. 取得文件與範圍

使用者提供 Datasheet，並指出要驗證的功能，即可開始。自行讀取檔名、料號與版本；不要求使用者整理章節、頁碼、指令表或暫存器索引。

- 已指定功能：直接閱讀文件並設計，功能摘要與規則放進計畫書供審查。不逐階段等待核可；使用者明確要求先討論時除外。
- 只有 Datasheet、沒有功能範圍：先自行閱讀目錄與功能清單，再一次詢問要驗證哪些功能。不能自行猜測哪一項是新功能。
- 缺少 Datasheet、文件無法讀取，或規格衝突使主要測試方向無法確定：集中詢問真正阻擋工作的事項。已提供的資料不再問。
- 其餘規格缺漏與設備條件：列入待確認清單，繼續設計有依據的部分，不用一長串問卷阻擋計畫產出。

依本次任務處理：全新功能直接建立計畫；提供現有流程時才做新舊對照；提供實測結果時只更新相關測項。只有 log 而沒有既有計畫時，依已提供的 Datasheet 對應相關功能與測項；無法對應的紀錄保留為未對應證據，不編造原計畫。缺少判定規格時只整理觀察與待確認。操作限制未提供時標「未提供」，不視為沒有任何限制。

完成條件：已取得可閱讀的規格與明確功能範圍，或已指出阻擋工作的具體原因。

### 先確定用途，再選測項

預設優先驗證新產品功能與邏輯，再依需求評選指定功能的 CP 測項；不自行擴成整顆產品的量產計畫。三種用途共用規格依據，但分開判斷是否納入：

- **產品功能驗證**：確認規格行為、重要操作與相關邊界是否正確。
- **非法／未定義用法探索**：保留使用者指定的目的與條件，觀察異常操作的結果與恢復能力。規格禁止與規格未定義分開判讀，不因真實使用者可能不會操作就刪除指定測試。
- **CP 量產篩選**：在功能邏輯驗證基礎上，評選可攔截製程或樣品差異所造成不良的測項，不把 DV 流程全部搬入 CP。

不要求時數預算、不估測試成本，也不因耗時或成本高而省略必要驗證。精簡依必要性、重複性與新增判別價值決定，不設固定測項數上限。

### 測項入選與停止擴充

先選測項，再撰寫完整流程。以下判斷由 AI 自行完成，不新增逐項核可關卡：

1. **保留指定範圍**：使用者指定的目的、位址、pattern、邊界或非法序列均保留；若規格或設備使其無法執行，明列限制，不偷偷刪除或更換條件。
2. **標明情境依據**：區分「使用者提供的實際用途」「可查證應用依據」「AI 推演」。使用者刻意指定的探索標為「使用者指定探索」，不冒充實際用途。沒有依據不得稱為常見或編造發生機率；Datasheet 的合法性不等於客戶使用頻率。
3. **說明不可取代性**：每項簡述要抓什麼錯誤，以及現有測項為何抓不到。AI 推演先列候選，只有具體說明新增判別價值與本次驗證必要性，才能選入完整流程；推測的失效機制仍標為假設。
4. **合併等效條件**：同一規則、觸發與判讀方式相同的位址、pattern 或指令排列，合併為一項的代表條件。只有條件會造成不同判斷才拆項；合併仍保留使用者指定條件。
5. **停止擴充**：無新增判別價值就合併或停止。有具體價值但尚未具備納入理由的，只留簡短補充候選與納入條件。四類測試是檢查角度，不是狀態 × 指令 × 長度的展開矩陣。

輸出分為「已選測項」與「補充候選」。僅已選測項展開完整操作；候選不生成 Flow 或逐步流程。重要的合併與未涵蓋取捨簡述一次，不列舉所有排列，也不以大量待確認問題代替篩選。

### CP 納入依據

需要 CP 建議時，逐項列出攔截目的、判定依據，以及「已有實測／失效案例支持」或「尚待驗證的攔截假設」。沒有證據時僅列 CP 候選；不因 DV 通過就宣稱量產篩選有效，也不強制每項 DV 對應 CP。已有證據仍須標明適用產品、條件與限制。

正式 CP PASS／FAIL 必須有已確認規格或 Designer 確認的工程要求。未定義用法沒有確認依據前只做觀察，不作正式篩選。只有功能預期正確，尚不足以證明可攔截製程或 Sample corner case；實測樣品不代表所有製程差異。

### 預設機台範圍

不安排高頻測試或外部 RESET、/HOLD、/WP pin 硬體控制。優先使用本產品支援的 Software Reset，保留必要等待、輪詢與復原檢查。真實 Power Down／Power Up 僅列「機台允許時的補充建議」，確認能力並納入範圍後才展開；不預設執行，也不以 Software Reset 結果替代。目標功能依賴被排除的硬體操作時，明列無法驗證的缺口。

### Writer 使用條件

使用者指定 Writer／Programmer 時，直接採以下條件，不再詢問是否具備 SPEED、上下電、/HOLD 或電源控制能力。未指定設備時維持一般功能計畫，不自行綁定 Writer，也不預設展開完整電性與時序驗證。

- **固定低頻**：使用已知可用且符合本次指令規格的低頻設定；不掃頻、不測最高速度、不做 SPEED 或時序裕量驗證。不自行指定通用 MHz 數值。計畫可記「沿用 Writer 低頻設定」，實作時由現有設定取得。
- **保留必要等待**：低頻不代表取消 Program／Erase 完成等待、狀態輪詢、timeout、Reset recovery time 或指令所需延遲。依 Datasheet 與可用函式實作，避免無限等待。
- **Software Reset**：一般重新初始化與復原流程使用本產品規格支援的 Software Reset。預設流程不安排 Power OFF/ON；補充上下電依前述機台範圍處理，不擴成掉電注入或電源斜率控制。依本次 Datasheet 決定指令、可接受狀態、等待及重設後讀回，不預設固定 opcode。
- **區分 Reset 與斷電**：Software Reset 不等同真正上下電，也不證明掉電恢復、上電初始化或斷電資料保留。真實上下電依預設機台範圍列補充建議，不進入預設 Writer 流程。若目標功能只能靠上下電驗證，保留缺口，不偽造替代測項。
- **不要求特殊硬體控制**：排除外部 /HOLD、/WP、硬體 Reset 腳位操作。不預設可程式電源、電壓／溫度掃描或精細時間窗口能力；只有明確納入目標並提供能力才擴充。需外部腳位控制的功能明列驗證缺口。
- **無法復原就停止**：不支援 Software Reset、目前狀態不接受該指令，或 Reset 後仍無法建立已知狀態時，停止相依測項並列待人工處理；不偷偷改用電源控制或 Test Mode。
- **交接**：先完成 HTML 計畫，明列低頻、Software Reset、範圍外項目與必要等待。使用者要求接續 Writer 實作時，再交給 writer_program_flow_design，傳遞計畫版本與上述限制。只要求計畫時交付到此為止。


## 2. 自行閱讀 Datasheet

1. 先查目錄與功能描述，再追查指令格式、位址、資料長度、狀態位元、保護條件、時序、Reset／斷電行為及跨章節限制。不要只讀單一章節。
2. 表格、註腳、波形或掃描頁無法以文字讀取時，使用可用的頁面渲染或 OCR，對照頁面檢查。仍無法辨識才請使用者補清晰文件，不猜數值。
3. 記下條文與文件版本。自行整理來源章節／頁碼；PDF 頁次與印刷頁碼不同時註明。來源放在對應規則旁或可展開的參考依據，避免每句都掛頁碼。
4. 將資訊分成「規格明訂」「本計畫的測試配置」「待確認」。測試配置如 pattern、合法測試位址與取樣方式可由 AI 提議，說明選擇理由；不得冒充產品規格。
5. 使用者提供的設計草案或 RD 確認內容可以作為補充，但標明版本、來源與確認狀態。現有程式、導讀與既有樣品行為不取代 Datasheet。

整理功能做什麼、合法前提、禁止行為、操作後可觀察的變化與未定義行為。內部可用規則編號追蹤涵蓋情況，正文以工程師容易閱讀的敘述為主。

完成條件：每個規格預期都有來源；不明確的行為已標待確認，沒有把推測寫成事實。

### 呈現產品狀態與判斷依據

先整理產品狀態，再設計測試順序。涉及保護、模式切換、Reset、Suspend 等狀態行為時，必須用 HTML／SVG 呈現「初始可觀察狀態 → 指令與成立條件 → 操作後狀態或維持不變」。正常、拒絕／忽略及未定義路徑依規格分開標示，不把未知行為畫成已確定結果。沒有相關狀態切換時，改用資料前後對照並說明原因。

每個重要狀態與切換要能對應規格規則或待確認問題。用工程師可觀察的資料、位元與模式命名；複雜圖分開呈現，不省略會改變判斷的條件，不以測試執行順序圖取代產品行為圖。

明列本次採用的假設、未涵蓋的狀態／條件及其影響，包括為簡化圖形而省略的路徑。圖上沒有問題，不代表未涵蓋範圍也沒有問題。

## 3. 設計測試構想並檢查漏測

設計時必讀 [測試設計檢查](references/test-design-review.md)，先依第 1 節完成入選與合併。沿功能狀態與操作順序檢查正驗、反驗、邊界與未定義用法四種角度；未選入的類別簡述重要理由，不為湊數產生測項。

- 正驗：在合法條件下證明功能成功，讀回資料與相關狀態。
- 反驗：每次改變一項前提，其餘保持合法。結果依規格決定，不一律假設拒絕指令或所有位元不變。
- 邊界：檢查相關的位址、長度、區域、時序、電源、模式與次數邊界，選擇界內、邊界與界外有判別能力的點。規格未定義的界外行為改列觀察項目。
- 未定義用法：明確區分可能結果與正式預期，列出觀察點及具體的「要問 Designer」問句，不以 AI 假設判產品 FAIL。

每個已選測項至少說明情境依據、要抓的錯誤與不可取代性、前置狀態、操作順序、讀回／量測位置、預期與判定方式。選擇可分辨的資料，確認未操作區域不受波及。補充候選僅列理由與納入條件。

將重要的可能異常寫成可審查的路徑：「初始狀態 → 操作順序 → 可能異常 → 違反的規則 → 哪個測項能發現」。另說明測項是否可能誤判通過，以及如何避免。未實測的路徑標為推演；沒有明確規格的行為列為待確認，不稱為已發現缺陷。沒有找到具體路徑時如實說明，不虛構反例。

共通條件寫一次，個別測項只補差異；細節應足以審查測試邏輯，不要求底層函式、程式變數、編譯方式或 printf 格式。

完成條件：每條已確認的重要功能規則都有測項或明確的未涵蓋說明；每個測項都能說明如何看出目標錯誤。

## 4. 組織流程

依「概念 → 流程 → 判讀」組織每個功能章節：

1. 功能概念與驗證目的。
2. 執行前要知道的事：會改動的資料與設定、永久性操作、尚未確認的操作限制。
3. 產品應該怎麼運作：規則與產品狀態／資料前後對照，依第 2 節呈現。
4. 共通方法：測試區域、pattern、讀回範圍與共用條件。
5. 測試流程總覽：各 Flow 的目的、順序與失敗分支。
6. 已選測項：以「步驟／做什麼／預期」表格為主，表前說明情境依據、要抓的錯誤與不可取代性；表後解釋關鍵判斷與重要異常路徑。
7. 已選邊界與未定義用法：可能結果、觀察點、要問 Designer；沒有已選項目時簡述即可，不強制建立 Flow X。補充候選另以短表呈現。需要 CP 建議時，另列其攔截目的、判定依據與證據狀態，不混作已證實的量產流程。
8. 復原與結果判讀：結束狀態、停止條件、必要的測試紀錄。
9. 假設、未涵蓋範圍及其影響、待確認與參考依據；有舊流程時才加差異與缺口說明。

用 Flow 0 表示預檢，其後依功能安排測試階段；邊界與探索項目可獨立為 Flow X，最後安排復原。Flow 數量與順序依功能決定，不照抄範例。步驟用 1.1、1.2 等編號，圖與表保持一致。

前置條件失敗時，不判產品功能失敗。停止相依測項，說明復原或人工處理方式。未知狀態須先恢復並讀回檢查，才能執行後續測試；無法恢復就停止。不要一律要求未知狀態下繼續測試。

永久鎖定、OTP 等操作要明列不可逆性與獨立樣品需求；Datasheet 未提供的 Test Mode 不得當成通用復原方法。無法回復時寫出實際結束狀態，不承諾回到出廠值。

## 5. 轉 HTML 前的文字改寫關卡（強制套用雙 Skill）

**嚴禁邊湊 HTML 標籤邊一次生成正文（禁止 One-shot 直接輸出 HTML）。** 在填入 [HTML 範本](assets/verification-plan-template.html) 之前，必須先完成各章節與測項表的文字草稿，並依文末「用詞與文字：必須套用第三方 skill」執行**第二輪實質改寫與結構檢查**：

1. **先跑 `speak-human-tw`（去 AI 味與台灣工程用語校準）**：
   - **砍除 AI 對 Prompt 交差的免責自白**：正文中禁止出現「此文件製作過程未操作晶片」「所有來源取自使用者提供檔案，未上傳 Datasheet」「本計畫不宣稱…」這類對系統規則交差的防禦性套話。
   - **禁止機械重複標籤**：測試配置或推演性質在章節開頭交代一次即可，禁止在 T1～Tn 每個測項開頭重複蓋章「AI 推演，依 R…」。
   - **台灣工程用語零混用**：依 `references/taiwan-localization.md` 統一詞彙。例如 `address` 一律寫「位址」（禁止混用「地址」「地址長度」「低地址區」），`data` 寫「資料」，`register` 寫「暫存器」，`default` 寫「預設」，`support` 寫「支援」。
2. **再跑 `asd-ste100`（繁體中文工程結構硬指標）**：
   - **全篇零分號（STE Rule 8.1）**：正文、圖說與表格內**完全禁止使用全形分號 `；`**（HTML 實體如 `&amp;` 除外）。原本以分號串接的複合句，一律拆成以句號 `。` 結尾的獨立短句，或改為項目清單。
   - **一物一名，禁止同義詞與別名輪替（STE Scan Checklist #1）**：同一測試目標頁、來源頁、暫存器或操作，全篇固定使用同一代稱（例如目標頁固定為 `T` 與 `T2`，禁止在 T5 叫 `T`、T6 改叫 `N`、T8 又改叫 `B` 再另外解釋是別名）。
   - **步驟表格採主動祈使句、一句一動作、不省略動詞（No Ellipsis）**：「做什麼」欄位必須有明確動詞（例如寫「送出 04h，讀回 SR-1 確認 WEL=0。」，禁止寫成省略動詞的電報殘句「04h，讀回 WEL=0」）。
   - **前置條件與禁止事項寫在動作之前（時間順序原則）**：例如寫「讀回前禁止送出 81h。直接送出 83h 讀取全部 256 bytes。」，禁止倒裝寫成「直接 83h 讀 Buffer，之前不能插入 81h。」。
   - **多條規則改列清單（STE List Rule）**：超過 3 個條件或跨測項共用規則時，必須改用 `<ul><li>` 條列，禁止用 `<br>` 或長段落把 5～8 條規則塞在同一段。

完成條件：草稿已通過上述兩階段改寫，確認無全形分號 `；`、無「地址」混用、無別名輪替、無 AI 交差式免責套話，才可進入下一節轉為 HTML。

## 6. 產出 HTML 計畫書

產出前必讀 [HTML 輸出規範](references/html-output.md)，並將通過第 5 節文字改寫的內容填入 [HTML 範本](assets/verification-plan-template.html)。範本沿用使用者 NOR_Flash_DV_Guide_V6.html 的章節導覽、深色版面、流程卡片、SVG 示意與測項表，只沿用呈現方式，不沿用案例的產品數值或實測結論。

預設交付一個可直接開啟、離線閱讀的完整 HTML 檔案。用內嵌 HTML／SVG 呈現流程與必要的資料區域圖，不產生 Mermaid 原始碼或依賴 Mermaid。多功能使用章節切換，單一功能不硬湊多章。

一般計畫保持設備中立，Writer 計畫明列第 1 節的使用條件。只說明需要記錄的資料與判讀方式，不輸出 Writer log 教學、C code、程式交接要求或任何已編譯宣稱。

產出是待工程師審查的計畫，不是已通過的驗證報告。沒有實測資料時，結果標「未執行」，不得假造 PASS、樣品 ID 或 Designer 確認。

完成條件：已寫出 HTML，圖表與測項一致、互動可用，沒有殘留範本提示、未替換佔位符或全形分號 `；`。

## 7. 審查、更新與交付

- 用檢查表自查後，在可用瀏覽器實際檢查章節切換、流程連結、窄螢幕與列印。環境無法開啟時，做結構檢查並如實說明未做視覺檢查。
- 執行靜態文字檢查：確認產出的 HTML 內全形分號 `；` 數量為 0、中國用語「地址」數量為 0、無重複「AI 推演，依」印章。
- 新計畫寫成新檔。使用者要求修改既有計畫時，保留其他章節，不在版本控制內則先備份。
- 回填實測時分開保留「原始預期／可能結果」「實測結果」「判定與依據」，不以實測值覆蓋預期。記錄料號、條件與版本，一顆樣品的結果不推廣到其他料號。同時更新首頁與各章的實測狀態，清楚列出已測與未測範圍。
- 未重現推演問題時，檢查模型、觸發條件、測試條件與觀察方式，不直接宣告模型錯誤或產品正常。
- 最終回覆連結 HTML，簡述涵蓋範圍、重要待確認事項、實測狀態，以及**本次套用 `speak-human-tw` 與 `asd-ste100` 的具體改寫對照摘要（至少列出 3～5 處「原初稿寫法 → 違反規則 → 改寫後定稿」）**，證明已完成第二輪文字修飾才轉出 HTML。只要求計畫時到計畫書完成即結束；使用者已要求接續 Writer 實作時，完成計畫後再使用 writer_program_flow_design，沿用已確認的範圍，不重新擴張測項。

- **asd-ste100**：輔助檢查句子結構、操作指示與用詞一致性。來源：https://github.com/danyuchn/asd-ste100-skill

### 如何編輯計畫書（Draft → Rewrite → HTML 三階段）

1. **第一階段（Draft）**：先整理規格與測試邏輯草稿。鎖定保護內容：料號、文件版本、章節／頁碼、數值、單位、位址、pattern、指令與 opcode、暫存器與位元名稱、測項編號、規則編號、判定代碼、來源網址及引述原文。Program、Erase、Read、Reset 等工程名稱保持一致。程式碼、log、HTML 標記、id 與連結目標不做語言改寫。
2. **第二階段（Rewrite — 依 `speak-human-tw` 自動化工作流的事後摘要模式）**：
   - 採用 `speak-human-tw` 的「辦公文書／報告」情境，移除空泛敘述、刪除 AI 對 Prompt 規則交差的自白句（如「此文件製作過程未操作晶片」）、移除每個測項開頭重複的「AI 推演，依 R…」印章、校正台灣工程用語（如「地址」改為「位址」）與全形標點。不加入故事、情緒、第一人稱立場或原文沒有的結論。
   - 採用 `asd-ste100` 的結構規則：
     - **禁用全形分號 `；`**（Rule 8.1），全部拆為獨立句號短句或 `<ul><li>` 清單。
     - **固定單一識別名稱**（Scan Checklist #1），同一目標頁（如 `T`、`T2`）全篇一致，禁止在不同測項換名。
     - **一句一動作、主動祈使句、補齊動詞**，禁止省略動詞的電報式殘句，並將禁止條件與前提放在動作之前。
     - **消除名詞化贅詞**（Rule 3.7），例如「進行…之驗證」改為「驗證…」，「完成…之確認」改為「確認…」。
3. **保留不確定性與判定條件（Keep Modality）**：必須保留前提、例外、時序先後、否定、適用範圍及不確定程度。「可能」「推測」「待確認」「未實測」不得改成確定事實，不能為縮短句子刪掉判定條件或把可能結果改成正式預期。
4. **第三階段（HTML 轉換與保真回讀）**：將改寫後的定稿填入 HTML 範本，逐項對照原始規格與改寫前內容，確認資訊沒有遺失或新增。同步檢查 SVG 圖中文字、測項表與判讀說明一致，並確認 HTML 內無殘留全形分號 `；`。
5. **規則衝突優先序**：優先保留事實、工程精確度與證據狀態，其次是本 skill 的測試設計與 HTML 結構，再套用 speak-human-tw 的語感及 asd-ste100 的句子結構。清楚比極短更重要。
6. **參考依據與事後摘要**：在計畫的參考依據中列出實際使用的兩份 skill repo 與版本／讀取日期，標為「文字編輯參考」，不混作產品規格依據。交付時附上「原初稿寫法 → 違反規則 → 改寫後定稿」的代表性摘要表，讓工程師一眼確認已完成雙 Skill 改寫。
