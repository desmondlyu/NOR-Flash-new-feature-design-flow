# NOR Flash DV Design

產出供工程師審查測試構想的驗證計畫書。完成標準是讀者能理解「為什麼測、怎麼測、看什麼、如何判斷」，不要求程式實作細節。本 skill 不產生測試程式，也不要求接續 Writer 或任何特定設備的 skill。

方法來源：[pstack /statechart](https://github.com/cursor/plugins/tree/main/pstack/skills/statechart)。

借用其「讓人審查產品狀態、沿操作路徑找出違反規則的可能性、再以實際行為核對」的方法。本 skill 以 HTML 呈現文件推演，不預設執行形式驗證或窮舉狀態，也不宣稱已證明產品正確。工程師審查 AI 對規格與設計意圖的理解；產出期間不增加逐階段核可。

開始撰寫計畫前，先依文末「用詞與文字」取得並讀取兩份文字編輯 skill；未安裝時仍須嘗試原 repo 讀取與搜尋備援。

## 1. 取得文件與範圍

使用者提供 Datasheet，並指出要驗證的功能，即可開始。自行讀取檔名、料號與版本；不要求使用者整理章節、頁碼、指令表或暫存器索引。

- 已指定功能：直接閱讀文件並設計，功能摘要與規則放進計畫書供審查。不逐階段等待核可；使用者明確要求先討論時除外。
- 只有 Datasheet、沒有功能範圍：先自行閱讀目錄與功能清單，再一次詢問要驗證哪些功能。不能自行猜測哪一項是新功能。
- 缺少 Datasheet、文件無法讀取，或規格衝突使主要測試方向無法確定：集中詢問真正阻擋工作的事項。已提供的資料不再問。
- 其餘規格缺漏與設備條件：列入待確認清單，繼續設計有依據的部分，不用一長串問卷阻擋計畫產出。

依本次任務處理：全新功能直接建立計畫；提供現有流程時才做新舊對照；提供實測結果時只更新相關測項。只有 log 而沒有既有計畫時，依已提供的 Datasheet 對應相關功能與測項；無法對應的紀錄保留為未對應證據，不編造原計畫。缺少判定規格時只整理觀察與待確認。操作限制未提供時標「未提供」，不視為沒有任何限制。

完成條件：已取得可閱讀的規格與明確功能範圍，或已指出阻擋工作的具體原因。

## 2. 自行閱讀 Datasheet

1. 先查目錄與功能描述，再追查指令格式、位址、資料長度、狀態位元、保護條件、時序、Reset／斷電行為及跨章節限制。不要只讀單一章節。
2. 表格、註腳、波形或掃描頁無法以文字讀取時，使用可用的頁面渲染或 OCR，對照頁面檢查。仍無法辨識才請使用者補清晰文件，不猜數值。
3. 記下條文與文件版本。自行整理來源章節／頁碼；PDF 頁次與印刷頁碼不同時註明。來源放在對應規則旁或可展開的參考依據，避免每句都掛頁碼。
4. 將資訊分成「規格明訂」「本計畫的測試配置」「待確認」。測試配置如 pattern、合法測試位址與取樣方式可由 AI 提議，說明選擇理由；不得冒充產品規格。
5. 使用者提供的設計草案或 RD 確認內容可以作為補充，但標明版本、來源與確認狀態。現有程式、導讀與既有樣品行為不取代 Datasheet。

整理功能做什麼、合法前提、禁止行為、操作後可觀察的變化與未定義行為。內部可用規則編號追蹤涵蓋情況，正文以工程師容易閱讀的敘述為主。

完成條件：每個規格預期都有來源；不明確的行為已標待確認，沒有把推測寫成事實。

### 呈現產品狀態與判斷依據

先整理產品狀態，再設計測試順序。涉及保護、模式切換、Reset、Suspend 等狀態行為時，必須用 HTML／SVG 呈現「初始可觀察狀態 → 指令與成立條件 → 操作後狀態或維持不變」。正常、拒絕／忽略及未定義路徑依規格分開標示，不把未知行為畫成已確定結果。沒有相關狀態切換時，改用資料前後對照並說明原因。

每個重要狀態與切換要能對應規格規則或待確認問題。用工程師可觀察的資料、位元與模式命名；複雜圖分開呈現，不省略會改變判斷的條件，不以測試執行順序圖取代產品行為圖。

明列本次採用的假設、未涵蓋的狀態／條件及其影響，包括為簡化圖形而省略的路徑。圖上沒有問題，不代表未涵蓋範圍也沒有問題。

## 3. 設計測試構想並檢查漏測

設計時必讀 [測試設計檢查](references/test-design-review.md)。沿功能狀態與操作順序推演，保留正驗、反驗、邊界與未定義用法四類；不適用的類別簡述原因，不為湊數產生測項。

- 正驗：在合法條件下證明功能成功，讀回資料與相關狀態。
- 反驗：每次改變一項前提，其餘保持合法。結果依規格決定，不一律假設拒絕指令或所有位元不變。
- 邊界：檢查相關的位址、長度、區域、時序、電源、模式與次數邊界，選擇界內、邊界與界外有判別能力的點。規格未定義的界外行為改列觀察項目。
- 未定義用法：明確區分可能結果與正式預期，列出觀察點及具體的「要問 Designer」問句，不以 AI 假設判產品 FAIL。

每個測項至少說明目的、前置狀態、操作順序、讀回／量測位置、預期與判定方式。選擇可分辨的資料，確認未操作區域不受波及。不要只列測項名稱或「檢查是否正常」。

將重要的可能異常寫成可審查的路徑：「初始狀態 → 操作順序 → 可能異常 → 違反的規則 → 哪個測項能發現」。另說明測項是否可能誤判通過，以及如何避免。未實測的路徑標為推演；沒有明確規格的行為列為待確認，不稱為已發現缺陷。沒有找到具體路徑時如實說明，不虛構反例。

共通條件寫一次，個別測項只補差異；細節應足以審查測試邏輯，不要求底層函式、程式變數、編譯方式或 printf 格式。

完成條件：每條已確認的重要功能規則都有測項或明確的未涵蓋說明；每個測項都能說明如何看出目標錯誤。

## 4. 組織流程

依「概念 → 流程 → 判讀」組織每個功能章節：

1. 功能概念與驗證目的。
2. 執行前要知道的事：會改動的資料與設定、永久性操作、尚未確認的操作限制。
3. 產品應該怎麼運作：規則與產品狀態／資料前後對照，依第 2 節呈現。
4. 共通方法：測試區域、pattern、讀回範圍與共用條件。
5. 測試流程總覽：各 Flow 的目的、順序與失敗分支。
6. 完整測項：以「步驟／做什麼／預期」表格為主，表前說明測試目的，表後解釋關鍵判斷與重要異常路徑，連到可發現問題的測項。
7. 邊界與未定義用法：可能結果、觀察點、要問 Designer。
8. 復原與結果判讀：結束狀態、停止條件、必要的測試紀錄。
9. 假設、未涵蓋範圍及其影響、待確認與參考依據；有舊流程時才加差異與缺口說明。

用 Flow 0 表示預檢，其後依功能安排測試階段；邊界與探索項目可獨立為 Flow X，最後安排復原。Flow 數量與順序依功能決定，不照抄範例。步驟用 1.1、1.2 等編號，圖與表保持一致。

前置條件失敗時，不判產品功能失敗。停止相依測項，說明復原或人工處理方式。未知狀態須先恢復並讀回檢查，才能執行後續測試；無法恢復就停止。不要一律要求未知狀態下繼續測試。

永久鎖定、OTP 等操作要明列不可逆性與獨立樣品需求；Datasheet 未提供的 Test Mode 不得當成通用復原方法。無法回復時寫出實際結束狀態，不承諾回到出廠值。

## 5. 產出 HTML 計畫書

產出前必讀 [HTML 輸出規範](references/html-output.md)，並以 [HTML 範本](assets/verification-plan-template.html) 為起點。範本沿用使用者 NOR_Flash_DV_Guide_V6.html 的章節導覽、深色版面、流程卡片、SVG 示意與測項表；只沿用呈現方式，不沿用案例的產品數值或實測結論。

預設交付一個可直接開啟、離線閱讀的完整 HTML 檔案。用內嵌 HTML／SVG 呈現流程與必要的資料區域圖；不產生 Mermaid 原始碼或依賴 Mermaid。多功能使用章節切換；單一功能不硬湊多章。

保持設備中立。只說明需要記錄的資料與判讀方式，不輸出 Writer log 教學、C code、程式交接要求或任何已編譯宣稱。

產出是待工程師審查的計畫，不是已通過的驗證報告。沒有實測資料時，結果標「未執行」，不得假造 PASS、樣品 ID 或 Designer 確認。

完成條件：已寫出 HTML，圖表與測項一致、互動可用，沒有殘留範本提示或未替換佔位符。

## 6. 審查、更新與交付

- 用檢查表自查後，在可用瀏覽器實際檢查章節切換、流程連結、窄螢幕與列印。環境無法開啟時，做結構檢查並如實說明未做視覺檢查。
- 新計畫寫成新檔。使用者要求修改既有計畫時，保留其他章節；不在版本控制內則先備份。
- 回填實測時分開保留「原始預期／可能結果」「實測結果」「判定與依據」，不以實測值覆蓋預期。記錄料號、條件與版本；一顆樣品的結果不推廣到其他料號。同時更新首頁與各章的實測狀態，清楚列出已測與未測範圍。
- 未重現推演問題時，檢查模型、觸發條件、測試條件與觀察方式，不直接宣告模型錯誤或產品正常。
- 最終回覆連結 HTML，簡述涵蓋範圍、重要待確認事項與實測狀態。工作到計畫書完成即結束，不自動呼叫其他實作 skill。

## 用詞與文字：必須套用第三方 skill

每次新建、修改或回填驗證計畫，都必須先嘗試取得並讀取以下兩份 skill，再套用其文字規則。不能只在環境已安裝時才選用，也不能只附來源連結卻沒有閱讀內容。

- **speak-human-tw**：主要用於自然、清楚的繁體中文與台灣用語。來源：https://github.com/Raymondhou0917/speak-human-tw
- **asd-ste100**：輔助檢查句子結構、操作指示與用詞一致性。來源：https://github.com/danyuchn/asd-ste100-skill

### 使用時機與取得順序

1. 開始撰寫功能摘要、狀態圖說明或計畫正文前，先讀 speak-human-tw，再讀 asd-ste100。涵蓋 AI 自行撰寫的必要提問、功能規則、流程圖文字、測項、預期結果、判讀、待確認事項與交付說明。簡短進度通知不必等待下載完成。
2. 已安裝時，從目前環境提供的 skill 位置讀取 SKILL.md 及相關參考文件。同一任務已完整讀過且未變更者可沿用，不必反覆下載。不要只憑名稱或記憶宣稱已套用。
3. 未安裝時，先從上述原始 repo 直接讀取 SKILL.md 與需要的參考文件。使用 repo 實際預設分支，不假設兩者都是 main。可使用 GitHub 連接工具、瀏覽工具或下載到本次工作暫存區；暫存讀取不等於永久安裝。
4. 直接讀取失敗時，使用 Web Search 搜尋完整 repo 網址及檔名，例如「Raymondhou0917/speak-human-tw SKILL.md」與「danyuchn/asd-ste100-skill SKILL.md」。開啟搜尋找到的原 repo 檔案，確認 owner 與 repo 名稱相符後讀取全文。搜尋摘要、第三方轉載或同名 skill 不可代替原文。
5. 至少讀取：
   - speak-human-tw：SKILL.md、references/patterns.md、references/taiwan-localization.md、references/protected-list.md；依 SKILL.md 的適用規則補讀其他參考文件。
   - asd-ste100：SKILL.md、references/writing-rules.md。
   檔案若搬移，以原 repo 的 SKILL.md 連結為準。部分參考文件不可讀時，依已取得的單檔備援規則處理，記錄缺少的檔案。
6. 下載與 Web Search 均失敗時，說明哪份 skill 或參考文件無法取得，使用本節的保真與簡明規則繼續完成計畫。在交付說明標「未套用〈skill 名稱〉」或「僅套用已取得的 SKILL.md，未讀取〈檔案〉」，不能宣稱完整套用。

### 下載與永久安裝

- 讀取即能用於本次計畫，不強制使用者安裝才能繼續。需要長期使用時，可一次說明缺少哪些 skill、上述 repo 網址及預定安裝位置；已明確授權安裝者直接辦理，否則取得同意後再永久安裝。不等待安裝決定也能先以原 repo 內容完成本次文字處理。
- 安裝使用目前平台支援的方式。一般檔案式環境，在平台可辨識的 skills 根目錄下，分別建立 speak-human-tw 與 asd-ste100 資料夾；若本 skill 位於該根目錄，可放在同層。每份保留 SKILL.md、所需 references 的相對路徑及原始授權檔案。不要只複製 SKILL.md 而漏掉它引用的文件。
- 平台若有專用安裝工具或受管理的 skill 目錄，依該平台流程處理，不臆測固定路徑。已有版本不得未經確認就覆蓋或升級。
- 下載文字規則不需要執行 repo 的腳本或安裝命令；不自動執行下載的程式。安裝後檢查檔案與參考連結可讀，並確認平台可辨識；只有暫存下載時，不宣稱已安裝。
- 記錄本次實際讀取的來源網址與可取得的版本或 commit；無法取得版本時記錄讀取日期，不編造版本。

### 如何編輯計畫書

1. 先整理規格與測試邏輯，再潤飾文字。先用 speak-human-tw 的「辦公文書／報告」情境，移除空泛敘述、校正台灣用語與中文標點，維持工程報告語氣。不加入故事、情緒、第一人稱立場或原文沒有的結論。
2. 再用 asd-ste100 檢查一句一個操作、主動語態、條件明確及同一用詞維持同一意義。ASD-STE100 是英文標準；繁體中文只借用結構原則，不套英文詞數限制或核准字典，也不宣稱符合正式 STE 認證。
3. 本計畫流程採「直接編輯、交付時摘要」：AI 自行潤飾其產生的內容，不將每句改寫變成新的核可關卡。使用者明確要求逐句審查或只標問題時，依該要求處理。修改既有計畫只動本次授權範圍。
4. 動筆前鎖定保護內容：料號、文件版本、章節／頁碼、數值、單位、位址、pattern、指令與 opcode、暫存器與位元名稱、測項編號、規則編號、判定代碼、來源網址及引述原文。Program、Erase、Read、Reset 等工程名稱保持一致；程式碼、log、HTML 標記、id 與連結目標不做語言改寫。
5. 必須保留前提、例外、時序先後、否定、適用範圍及不確定程度。「可能」「推測」「待確認」「未實測」不得改成確定事實；不能為縮短句子刪掉判定條件或把可能結果改成正式預期。
6. 潤飾後逐項對照原始規格與改寫前內容，確認資訊沒有遺失或新增。同步檢查圖中文字、測項表與判讀說明一致。表格與編號有助審查測試流程時保留，不因去 AI 味而刪除。
7. 規則衝突時，優先保留事實、工程精確度與證據狀態，其次是本 skill 的測試設計與 HTML 結構，再套用 speak-human-tw 的語感及 asd-ste100 的句子結構。清楚比極短更重要。
8. 在計畫的參考依據中列出實際使用的兩份 skill repo 與版本／讀取日期，標為「文字編輯參考」，不混作產品規格依據。交付時簡述文字調整與未能套用的項目，不要求使用者審查整份逐句修改清單。
