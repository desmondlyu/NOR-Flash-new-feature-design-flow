# NOR Flash DV Design

把 NOR Flash 的 Datasheet 變成工程師一眼看得懂、查得回依據的單檔 HTML 驗證計畫書。完成標準很單純：讀者打開檔案，就能馬上搞懂「為什麼測、怎麼測、看哪裡、怎麼判讀」，不需要先看懂底層程式碼。本 skill 不產生測試程式，也不自動綁定 Writer 或特定機台。

| 步驟 | 做什麼 | 產出重點 |
| :-- | :-- | :-- |
| 1. 讀規格定範圍 | AI 自己查 Datasheet 的指令、暫存器、保護與時序 | 分清楚「規格明訂」「測試配置」「待確認」 |
| 2. 釘好固定位址 | 依容量與有效視窗算出固定的「頭、中、尾」基準區 | 不同計畫落點一致，不再每次亂跳位址 |
| 3. 畫狀態抓漏測 | 先畫晶片狀態圖，再從正驗、反驗、邊界、未定義篩選測項 | 合併重複項目，寫出異常路徑與防誤判方法 |
| 4. 雙技能改寫草稿 | 轉 HTML 前先用 `speak-human-tw` 與 `asd-ste100` 潤飾檢查 | 台灣工程用語、全篇零全形分號、一句一動作 |
| 5. 輸出單檔 HTML | 每個 Flow 配一張直白好讀的內嵌 SVG 圖，圖表雙向跳轉 | 離線可讀、可列印、無實測時標「未執行」 |

方法來源：[pstack /statechart](https://github.com/cursor/plugins/tree/main/pstack/skills/statechart)。借用它「先看產品狀態、順著操作路徑找可能違規點、再核對實際行為」的審查思路。這裡用 HTML 呈現文件推演，讓工程師核對 AI 對規格與設計意圖的理解，不執行形式驗證或窮舉所有狀態，也不代表已證明晶片無誤。產出過程一次完成，除非使用者明確要求先討論，否則不逐階段停下來等核可。

開始寫計畫前，必須先依文末「用詞與文字」取得並讀取兩份文字編輯 skill。本機未安裝時，依序從原 repo 與搜尋備援讀取。

## 1. 取得文件與範圍

使用者給了 Datasheet 並講明要測哪個功能，就可以直接動工。AI 自己讀取檔名、料號、版本、章節、頁碼、指令表與暫存器索引，不要叫使用者先幫忙整理目錄。

- **已指定功能**：直接讀規格並設計，把功能摘要與規則放進計畫書供審查。除使用者要求先討論外，不中途停等核可。
- **只有 Datasheet、沒說測哪個功能**：先讀完目錄與功能清單，再一次問清楚要驗證哪些功能，不自己亂猜哪一項是新功能。
- **缺 Datasheet、檔案讀不到，或規格互相衝突導致主方向定不下來**：把真正卡住的問題集中問一次。已經給過的資訊不再重問。
- **其他規格缺漏與機台條件**：直接列進「待確認清單」，繼續設計有依據的部分，不要丟出一長串問卷擋住產出。

依當次任務分流處理：新功能直接建新計畫。有給舊流程才做新舊對照。有給實測結果只更新相關測項。若只有實測 log 而沒有舊計畫，就對照 Datasheet 歸類相關功能與測項，對不上的紀錄保留為未對應證據，不編造原計畫。缺少判定規格時只整理觀察與待確認。操作限制沒提供時標「未提供」，不能當成沒有任何限制。

完成條件：已拿到可讀規格與明確功能範圍，或已具體指出卡住的原因。

### 先確定用途，再選測項

預設先驗證新產品功能與邏輯，有需要時再評選該功能的 CP 測項，不自動擴大成整顆晶片的量產計畫。三種用途共用同一份規格依據，但各自獨立判斷要不要納入：

| 用途 | 核心目標 | 判讀原則 |
| :-- | :-- | :-- |
| **產品功能驗證** | 確認規格明訂行為、關鍵操作與相關邊界是否正確 | 有明確條文依據，符合判 PASS，違反判 FAIL |
| **非法／未定義用法探索** | 保留使用者指定的異常操作，觀察晶片反應與恢復能力 | 分開標示「規格禁止」與「規格未定義」，不因客戶少用就刪掉指定測試 |
| **CP 量產篩選** | 挑出能攔截製程或晶粒差異不良的測項 | 不把 DV 全搬進 CP，缺證據時只列 CP 候選 |

不問時數預算、不估測試成本，也不因為耗時就省掉必要驗證。刪減只看必要性、是否重複與有沒有新增判別價值，不設固定測項數上限。

### 測項入選與停止擴充

先篩完測項，再寫完整步驟。以下篩選由 AI 直接完成，不逐題停下來問：

1. **保留指定範圍**：使用者指定的目的、位址、pattern、邊界或非法序列全部保留。若規格或設備限制做不到，清楚寫出限制，不偷偷刪改條件。
2. **標明情境依據**：分清楚「使用者提供的實際用途」「可查證應用依據」「使用者指定探索」「AI 推演」。沒有依據就不能寫成「常見用法」或編造發生機率，Datasheet 允許的操作也不自動等於客戶常用操作。
3. **講清楚不可取代性**：每一項都要能回答「要抓什麼錯」以及「為什麼其他測項抓不到」。AI 推演先放候選，只有具體說出新增判別價值與本次必要性的項目，才進入完整流程。推測的失效機制一律標明為假設。
4. **合併等效條件**：同一條規則、觸發方式與判讀結果都相同的位址、pattern 或指令排列，合併成一個代表條件。固定頭、中、尾三個基準區不代表每個測項都要重跑三次。只有位置或條件會改變規格判斷時才拆項，合併時仍保留使用者指定的條件。
5. **沒新價值就停**：不再多出判別價值就合併或停止。有具體價值但還缺納入條件的項目，只留簡短的「補充候選」與納入條件。正驗、反驗、邊界、未定義是四個檢查角度，不是「狀態 × 指令 × 長度」硬乘出來的展開矩陣。

輸出分成「已選測項」與「補充候選」。只有已選測項才畫 Flow 圖、寫逐步操作表。重要的合併與未涵蓋取捨簡述一次就好，不列舉所有排列組合，也不用一堆待確認問題代替篩選。

### CP 納入依據

需要給 CP 建議時，逐項寫明攔截目的、判定依據，以及屬於「已有實測／失效案例支持」還是「尚待驗證的攔截假設」。沒有證據就只列 CP 候選，不能因為 DV 通過就宣稱量產攔截有效，也不必硬讓每個 DV 測項都對到 CP。就算有既有案例，也要註明適用料號、條件與限制。

正式的 CP PASS／FAIL 必須有已確認規格或 Designer 確認的工程要求。未定義用法在確認前只做觀察，不當正式淘汰依據。功能預期正確不等於能攔住製程變異，單顆樣品的結果也不能直接代表所有晶粒。

### 預設機台範圍

預設不排高頻測試，也不動外部 `/RESET`、`/HOLD`、`/WP` 硬體腳位。重新初始化與復原優先用本產品支援的 Software Reset，並保留必要的等待、輪詢與復原檢查。真正的 Power Down／Power Up 只列在「機台允許時的補充建議」，等確認設備能力並納入範圍後才展開，不預設執行，也不能拿 Software Reset 的結果充當斷電驗證。若目標功能非靠這些排除的硬體操作不可，直接寫明驗證缺口。

### Writer 使用條件

只要使用者指定 Writer／Programmer，就直接套用下列條件，不必再問有沒有 SPEED、上下電、`/HOLD` 或電源控制能力。沒指定設備時保持設備中立，不自己綁定 Writer，也不預設展開完整的電性與時序測試。

- **固定低頻**：使用已知可用且符合指令規格的低頻設定，不掃頻、不測最高速度、不做 SPEED 或時序裕量驗證，也不自己隨便填一個 MHz 數字。計畫裡記「沿用 Writer 低頻設定」，實作時再從現有設定讀取。
- **保留必要等待**：低頻不等於不用等。Program／Erase 完成等待、狀態輪詢、timeout、Reset recovery time 與指令延遲都要照 Datasheet 保留，避免無限卡死。
- **Software Reset**：一般重新初始化與復原用本產品支援的 Software Reset。預設不排 Power OFF／ON，也不擴張成掉電斜率或壓降注入控制。指令碼、可接受狀態、等待時間與重設後讀回都依本次 Datasheet 決定，不寫死固定 opcode。
- **分清楚 Reset 與斷電**：Software Reset 不是真正斷電重開，不能證明掉電恢復、上電初始化或斷電資料保存。若目標功能只能靠真實上下電驗證，保留缺口，不編造替代測項。
- **不要求特殊硬體控制**：排除外部 `/HOLD`、`/WP`、硬體 Reset 腳位控制，也不預設有可程式電源、電壓／溫度掃描或微秒級精準觸發視窗。只有使用者明確納入目標並提供設備能力時才擴充，做不到的部分明列驗證缺口。
- **救不回來就停**：產品不支援 Software Reset、當前狀態不接受該指令，或重設後還是回不到已知狀態時，立刻停止相依測項並列待人工處理，不偷偷改用電源控制或 Test Mode。
- **交接給 Writer**：先完成 HTML 計畫，清楚列出低頻、Software Reset、測試位址基準區與例外依據、範圍外項目與必要等待。等使用者要求接續寫 Writer 程式時，再交給 `writer_program_flow_design`，傳遞計畫版本、已確認的測試位址配置與上述限制。只要求計畫時就停在這裡。

## 2. 自行閱讀 Datasheet

1. 先看目錄與功能介紹，再一路追查指令格式、位址、資料長度、狀態位元、保護條件、時序、Reset／斷電行為與跨章節限制，不要只看單一章節就下結論。
2. 表格、註腳、波形圖或掃描頁讀不出文字時，用頁面渲染或 OCR 對照原頁檢查。真的辨識不出來才請使用者補清晰檔案，絕不猜數字。
3. 記下條文與文件版本，自己整理章節與頁碼（PDF 頁次跟印刷頁碼不同時要註明）。來源放在對應規則旁或可展開的參考區塊，不用每句話尾巴都掛頁碼。
4. 把所有資訊分進三個籃子：「規格明訂」「本計畫的測試配置」「待確認」。pattern 與取樣方式可由 AI 提議並說明理由。主記憶陣列的合法測試位址一律依第 4 節「固定測試位址基準區」由產品有效視窗與配置單位確定性算出，禁止每次隨機挑選分散位址。所有提議配置都不能冒充產品規格。
5. 使用者給的設計草案或 RD 確認紀錄可以當補充，但要標明版本、來源與確認狀態。既有程式碼、導讀文件或手邊樣品的表現，都不能取代 Datasheet。

整理清楚這個功能做什麼、合法前提是什麼、禁止什麼、做完可觀察到什麼變化，以及哪些地方規格沒寫。內部可以用規則編號追蹤涵蓋率，正文則用工程師好讀的白話敘述呈現。

完成條件：每個規格預期都有出處，沒寫清楚的行為都已標待確認，沒有把推測寫成事實。

### 呈現產品狀態與判斷依據

先畫清楚晶片怎麼變，再排測試怎麼跑。只要涉及保護、模式切換、Reset、Suspend 等狀態變化，就用內嵌 HTML／SVG 畫出「初始可觀察狀態 → 指令與成立條件 → 操作後狀態或維持不變」。把正常路徑、拒絕／忽略路徑與未定義路徑分開標示，不要把未知行為畫得像確定結果。如果功能本身沒有狀態切換，改畫「操作前後資料對照圖」並說明原因。

圖上的每個重要狀態與箭頭都要對得到規格規則或待確認問題，並用工程師讀得到的資料、位元與模式名稱命名。圖太擠就拆圖，不要為了簡化把會影響判斷的條件藏起來，也不要拿「測試步驟順序圖」冒充「產品狀態行為圖」。

清楚寫出本次採用的假設、沒涵蓋到的狀態／條件與影響（包含為了讓圖好讀而省略的分支）。圖上沒畫出問題，不代表沒畫到的地方就沒問題。

## 3. 設計測試構想並檢查漏測

動手設計時必讀 [測試設計檢查](references/test-design-review.md)。先照第 1 節篩選合併，再順著產品狀態與操作順序檢查四個角度（沒選進來的角度簡述原因即可，不為湊齊四類硬生測項）：

- **正驗**：條件全部合法時，證明功能真的有跑成功，讀回資料與狀態位元確認。
- **反驗**：每次只改壞一項前提，其他保持合法。預期結果照規格條文寫，不要一律假設晶片會拒絕指令或所有位元都不動。
- **邊界**：檢查位址、長度、區域、時序、電源、模式與次數的界內、邊界與界外點。規格沒定義的界外反應列為觀察項目。
- **未定義用法**：分清楚「可能出現的結果」與「正式規格預期」，寫出觀察點與一句具體的「要問 Designer」問題，不拿 AI 自己的假設判產品 FAIL。

每個已選測項都要寫清楚：情境依據、要抓的錯誤與不可取代性、前置狀態、操作順序、讀回／量測位置、預期結果與判定方式。挑選看得見差異的測試資料，並檢查沒動到的鄰近區域有沒有被波及。補充候選只寫理由與納入條件。

把關鍵的潛在異常寫成好審查的短鏈條：「初始狀態 → 操作順序 → 可能異常 → 違反的規則 → 哪個測項能抓到」，同時交代這個測項會不會誤判通過、怎麼防範。沒實測過的路徑標「推演」，沒規格的行為標「待確認」，不要直接叫它產品缺陷。沒找到具體異常路徑就老實說，不硬編反例。

共通條件在開頭寫一次就好，個別測項只寫差異點。細節夠讓工程師審出測試邏輯即可，不寫底層 C 函式名、變數、編譯參數或 `printf` 格式。

完成條件：每條重要規則都有對應測項或未涵蓋說明，每個測項都說得清楚怎麼抓出目標錯誤。

## 4. 組織流程

每個功能章節都照「概念 → 流程 → 判讀」的順序排好，讓讀者順著往下看就能讀懂：

1. **功能概念與驗證目的**：一句話講白這個功能在做什麼、這次要抓什麼錯。
2. **執行前要知道的事**：會改到哪些區段與設定、有沒有不可逆操作、有哪些操作限制還沒確認。
3. **產品應該怎麼運作**：規格規則與產品狀態圖（或資料前後對照圖）。
4. **共通方法**：固定基準測試區表格、測試資料圖樣（pattern）、讀回檢查範圍與共用條件。
5. **測試流程總覽**：各個 Flow 的目的、先後順序與失敗時的走向。
6. **已選測項**：以「步驟／做什麼／預期」表格為主。表前講情境依據、要抓的錯與不可取代性，表後補關鍵判讀與異常路徑。
7. **已選邊界與未定義用法**：列出可能結果、觀察點與「要問 Designer」的具體問題。沒有已選項目時簡述即可，不用硬開 Flow X。補充候選另外放一張短表。需要 CP 建議時獨立成區，寫明攔截目的、判定依據與證據狀態，不混充正式量產流程。
8. **復原與結果判讀**：結束時應該停在什麼狀態、什麼情況要立刻停測、最少要留哪些紀錄。
9. **假設、未涵蓋範圍、待確認與參考依據**：有舊流程時才加新舊差異與缺口對照。

Flow 0 固定放預檢與前置資料，後面依功能排各階段測試，邊界與探索可獨立成 Flow X，最後接復原階段。Flow 總數跟著功能走，不死背範例。步驟用 `1.1`、`1.2` 編號，讓 SVG 圖與表格完全對齊。

預檢或前置條件沒過時，不算產品功能 FAIL，應直接停止相依測項並說明復原或人工排查方式。測試中途若掉進未知狀態，必須先恢復並讀回確認，才能往下跑，救不回來就停，不要在未知狀態下硬跑後續測項。

永久鎖定、OTP 等不可逆操作要醒目標示並要求獨立樣品。Datasheet 沒寫的 Test Mode 不能拿來當通用復原手段。真的無法還原時，老實寫出結束狀態，不承諾回到出廠值。

### 固定測試位址基準區

把整塊可測的主記憶陣列（Main Cell）想成一把尺。只要任務不是全晶片掃描，使用者也沒有另外指定位址，測試位置就一律釘在尺上的**「頭、中、尾」三個固定書籤**，讓每一份驗證計畫與後續 Writer 程式都打在固定、好預期的位置，不再每次隨機挑位址。不帶陣列位址的純暫存器或狀態指令，不必硬湊陣列位址。

以常見的 `32Mb`（有效容量 `400000h` bytes）、最小抹除單位 `4KB Sector`（`1000h` bytes）為例，三個固定書籤長這樣：

```text
[ 頭基準區 ]                      [ 中基準區 ]                      [ 尾基準區 ]
000000h～000FFFh                  200000h～200FFFh                  3FF000h～3FFFFFh
(第 1 個 4KB Sector)              (正中央偏右第 1 個 4KB Sector)     (最後 1 個 4KB Sector)
└ 後鄰對照：001000h～001FFFh       ├ 前鄰對照：1FF000h～1FFFFFh       └ 前鄰對照：3FE000h～3FEFFFh
                                  └ 後鄰對照：201000h～201FFFh
```

產出計畫前，先從 Datasheet 查清楚產品實際有效容量（一律換成 bytes，注意區分 Mb 與 MB）、Page 大小 `P`、各抹除與保護單位地圖、Die 映射與選擇方式，以及目前的位址模式與選擇器狀態，再按下面規則算出唯一位址：

- **第一步：先算有效視窗 `[S, S + C)` 與配置單位 `U`**
  - 有效視窗 `[S, S + C)` 永遠取三個範圍的交集：「產品實際有效主陣列範圍」「目前位址模式及已確認或已建立的 Extended Address Register（EAR）、Bank、Die 選擇器可達範圍」「本次獲授權可操作範圍」（一般線性全陣列起點 `S = 0`、長度為 `C`）。下面的容量、模式與多 Die 規則都不能擴大這個交集，也不能把 3-Byte 欄位最大可表達的 `16 MiB` 直接當成小容量產品的實體容量。選擇器初始狀態未知時，要在 Flow 0 讀取建立或列為前置待確認。
  - 區域配置單位 `U` 跟單次指令讀寫長度分開定義。Sector／Block Erase 與區塊保護直接用該指令對應的合法單位當 `U`。一般主陣列 Page 讀寫因為前後要獨立抹除與復原，預設固定用規格確認的「最小可獨立抹除單位」（常見為 4KB Sector）當 `U` 來定位頭、中、尾。測試目的需要其他配置單位時列為例外並寫明理由，無法確認配置單位時列待確認。
- **第二步：套公式算出頭、中、尾與相鄰對照區**
  - **均一單位地圖**（有效視窗由 `N = C / U` 個等大合法單位組成，單次操作需連續整數 `k` 個單位，`1 <= k <= N`）：
    - **頭基準區（Head / Bottom）**：`[S, S + k × U)`（從起點算起前 `k` 個單位）。
    - **中基準區（Middle）**：`[S + floor(N / 2) × U, S + (floor(N / 2) + k) × U)`（偶數單位固定取中線右側第 1 個單位。若加上 `k` 後超出 `S + C`，改退回尾端合法起點並揭露重疊）。
    - **尾基準區（Tail / Top）**：`[S + (N - k) × U, S + C)`（最後 `k` 個完整單位，絕不超出 `S + C`）。
  - **鄰區對照與小容量防撞**：先定好上面的完整目標操作區間，再挑緊貼目標外側的前一個合法單位與後一個合法單位，當作「不該被改動」的對照區。超出 `[S, S + C)` 的那一側標為「無該側合法鄰區」，禁止生出負數或越界位址。`N < 3` 時合併重複基準區。當 `N < 5` 或 `k > 1` 讓候選鄰區撞上其他目標區時，優先保留目標區，取消或合併撞車那一側的對照，並在共通方法老實寫出獨立單位數與缺少對照區的限制，不可宣稱已驗證該側不波及。
  - **非均一單位與規格排除區**：當頭尾與中間的抹除單位大小不同，或規格明訂某些位址不支援該指令時，不能直接除 `C / U`，改照規格的合法單位地圖挑：頭取有效視窗內第 1 個支援該指令的完整單位，尾取最後 1 個，中取包含中點 `S + floor(C / 2)` 的合法完整單位（中點剛好壓在邊界上就取右側）。如果中點位置沒有支援該指令的合法單位，**先取中點右側起點最小的合法單位，右側也沒有才取左側終點最大的合法單位**，並註明原因。前後鄰區同樣從合法單位地圖挑，若中間隔著不支援區，要寫明兩者並非實體緊鄰，不宣稱已測到該交界。
  - **基準區內怎麼選 Page**：在選好的基準區內只操作單頁或少數幾頁時，固定從 `區起點` 開始依序拿 `區起點`、`區起點 + P`、`區起點 + 2P`（只有 `P = 100h` 時才寫 `+000h`、`+100h`、`+200h`），完整頁不可超出該基準區。如果要抽查整個區塊的首尾代表頁，固定取第一頁 `區起點` 與最後一頁 `區起點 + 實際單位長度 - P`，不要隨便挑中間的偏移頁。
- **第三步：決定這次要用 1 區、3 區還是全晶片（三層選用原則）**

| 測試類型 | 怎麼選區 | 為什麼這樣定 |
| :-- | :-- | :-- |
| **單區功能邏輯**（跟陣列高低位置無關，如狀態門檻、忙碌忽略、單頁 Buffer 內部讀寫） | 預設只用有效視窗內的**「中基準區」1 個單位**（仍須核對它是否非全零及兩側有無合法鄰區）。若要順便抓位址清零誤寫，且頭基準區在有效視窗內不重疊，可把「頭基準區」列為被動讀回對照區 | 避開零位址遮蔽，又不用把一模一樣的步驟無謂乘以三倍 |
| **空間代表性與跨區對稱驗證**（如讀寫抹除代表涵蓋、跨區保護對稱、混合粒度、位址模式切換） | 從固定的**頭、中、尾**挑出能區分目標規則的必要位置。需要三區代表涵蓋或使用者指定三區時就三區全用，其餘照判別價值保留或合併 | 覆蓋高低位址與區段差異，同時服從第 1 節等效合併原則，不硬跑三次 |
| **全晶片與全單元要求**（如 Whole-Chip 操作、讀回全部個別保護位元） | 照規格要求覆蓋完整範圍，並分開寫明「操作影響範圍」與「讀回觀察範圍」 | 不能拿頭、中、尾三點取樣冒充已經測完全晶片 |

- **位址模式、多容量共用 Datasheet 與多 Die 處理**
  - 分開記錄「完整邏輯位址」與「指令實際送出的傳輸位址欄位」，絕不能為了塞進 3-Byte 指令就砍掉高位元。容量 `<= 128Mb` 且採 3-Byte 模式時固定寫 6 位十六進位。容量 `>= 256Mb` 或採 4-Byte 模式時，完整邏輯位址固定寫 8 位十六進位。若用 3-Byte 指令搭配 EAR、Bank 或 Die Select 存取高區，要同時寫出 8 位邏輯位址、選擇器設定值與 6 位傳輸位址。當 `>= 256Mb` 產品處於未切 Bank 的預設 3-Byte 模式（包含 Software Reset 後回到預設且已確認 `EAR=00h`），而待測功能根本不測高位址或 4-Byte 擴展時，不要強迫無關測項切進 4-Byte 或改 Bank：只要實體範圍與獲授權範圍都完整包含低 `16 MiB`，有效視窗就是 `00000000h～00FFFFFFh`（對應 6 位傳輸位址 `000000h～FFFFFFh`），否則用實際交集，並具體列出視窗外沒測到的範圍。
  - 同一份 Datasheet 包了多種容量、使用者又沒指定單一料號時，先挑能涵蓋待測功能的最小正式容量來算基準位址（例如要測 `> 128Mb` 高位址功能就挑最小的 `>= 256Mb` 容量），在共通方法寫明代表容量與算式，同時把「實際目標料號與容量」列進待確認清單。
  - 多 Die（Stack Die）產品只有在整顆封裝邏輯範圍都可達且獲授權時，才對整顆封裝取一組頭、中、尾，否則照本次有效視窗選點，不因封裝總容量擴大操作範圍。若待測狀態或指令以單顆 Die 為獨立單位，就按各 Die 獲授權的有效範圍套公式，每顆 Die 預設取它的「中基準區」當代表點，不自動乘三倍。若產品靠指令切換 Die ID 而非線性連續定址，每顆 Die 內部起點從 `0` 算起，並強制寫明目標 Die ID。
- **允許偏離或加測的 6 種明確例外**（必須在共通方法寫出確切位址與理由）：
  - 使用者已明確指定的位址、範圍，或既有對照流程裡原本就固定的位址。
  - 保護規則（BP、TB、CMP、SEC、WPS 個別保護）算出的實際保護分界內側與外側相鄰單位。
  - OTP、Security Register、SFDP、Unique ID 等規格定義的專屬位址空間。
  - 跨頁回繞（Wrap）、跨 Sector／Block、跨 128Mb 邊界或跨 Die 交界的兩側相鄰位置。
  - 位址線獨立性或位元別名診斷所需的成對位址。
  - Datasheet 明訂不支援區或出廠保留區，照前面的「非均一單位與規格排除區」順序選替代點。但如果是**樣品本身存有未知保留資料、既有非揮發／OTP 鎖定，或可操作授權範圍不明**，一律寫「**測試位址待確認**」，嚴禁自動換區、抹除保留資料或私自解除保護。

### 測項敘述與流程示意圖

「頭、中、尾」只用來說明區域角色。正文、表格與圖片裡，都必須直接寫出換算後的確切十六進位位址或範圍、資料長度、資料內容與必要條件，同一個區域從頭到尾用同一種寫法。禁止用 `T`、`T1`、`T2`、`N`、`B` 這類自創目標代號代替位址說明，也禁止寫「該頁」「同上」叫讀者自己往上翻。Flow 編號、步驟編號、測項／規則追溯碼與 HTML 內部 `id` 可以保留定位，但旁邊仍要寫完整名稱。

必要的指令名稱、opcode、暫存器與位元值都要留著並順手寫明意思，例如寫「確認寫入致能位元 WEL=1」。共通背景在章節開頭寫一次，但每個步驟仍要寫出該步判定少不了的位址、資料與條件。

確切位址的來源要分清楚：是規格明訂、使用者指定、固定基準區算式，還是有寫明理由的例外配置。碰到未知保留資料、OTP 或未授權鎖定限制時，直接寫「測試位址待確認」。需要時補上 Die ID、選擇器狀態、位址模式與傳輸位址長度，絕不自己瞎編數字。

正文與圖表裡，用完整的中文時間意義取代冷冰冰的時序符號。例如寫「等待頁面寫入完成」，接著交代輪詢哪個暫存器與位元、什麼狀態算完成、超時上限依據是什麼、超時怎麼處理。典型值、最大值與工程設定要分開標示，不能把典型值當最大等待時間，沒依據就列待確認。原始時序符號（如 `tPP`）只留在可展開的來源對照裡，方便查規格與後續寫程式核對。

每個納入執行計畫的 Flow（包含 Flow 0 預檢、功能測試、已選探索與復原），不論實測了沒，都要在 Flow 標題與測項表之間放至少一張專屬的內嵌 SVG 流程示意圖。圖面採用「圖塊清楚、字少好讀」原則：一個方塊講清一件事（起始位址與資料、關鍵條件、指令順序、該變／不該變的區域、失敗停止或復原走向），太複雜就拆成兩張圖，詳細步驟交給底下的測項表補齊，不要把整張表塞進圖裡。產品狀態圖仍須獨立畫，補充候選則不畫 Flow 圖。

總覽卡片連到各 Flow，Flow SVG 裡的操作節點連到對應的測項表列，表列再連回原圖。連結文字要寫清楚目的地名稱與位址。跨章節跳轉先切到目標章節再捲動定位。支援鍵盤操作與清楚焦點框，關掉 JavaScript 時所有章節與錨點依然能讀能點，列印時保留標題、位址與圖表對應關係。

## 5. 轉 HTML 前的文字改寫關卡（強制套用雙 Skill）

**嚴禁邊湊 HTML 標籤邊一次生出正文（禁止 One-shot 直接輸出 HTML）。** 填入 [HTML 範本](assets/verification-plan-template.html) 之前，必須先寫完各章節與測項表的文字草稿，再照文末「用詞與文字」跑完**第二輪實質改寫與結構檢查**：

1. **先跑 `speak-human-tw`（去 AI 味與台灣工程用語校準）**：
   - **砍掉對系統規則交差的免責套話**：正文裡禁止出現「此文件製作過程未操作晶片」「所有來源取自使用者提供檔案，未上傳 Datasheet」「本計畫不宣稱…」這類寫給 Prompt 看的自白句。
   - **不重複蓋印章**：測試配置或推演性質在章節開頭講一次就好，禁止在每個測項開頭機械重複「AI 推演，依 R…」。
   - **台灣工程用語零混用**：照 `references/taiwan-localization.md` 統一詞彙。例如 `address` 一律寫「位址」（禁止混用「地址」「地址長度」「低地址區」），`data` 寫「資料」，`register` 寫「暫存器」，`default` 寫「預設」，`support` 寫「支援」。
2. **再跑 `asd-ste100`（繁體中文工程結構硬指標）**：
   - **全篇零全形分號（STE Rule 8.1）**：正文、圖說與表格內**完全禁止出現全形分號**（HTML 實體如 `&amp;` 除外）。原本用分號串起來的長句，一律拆成句號結尾的短句，或改列清單。
   - **一物一名**：同一個工程名稱與確切位址全篇寫法一致，不用單字母代號指稱頁面或資料。
   - **步驟表用主動祈使句、一句一動作、不漏動詞（No Ellipsis）**：「做什麼」欄位每句都要有明確動詞（例如寫「送出 04h，讀回 SR-1 確認 WEL=0。」，不寫成沒頭沒尾的電報句「04h，讀回 WEL=0」）。
   - **前提與禁止事項寫在動作前面（時間順序原則）**：例如寫「讀回前禁止送出 81h。直接送出 83h 讀取全部 256 bytes。」，不倒裝寫成「直接 83h 讀 Buffer，之前不能插入 81h。」。
   - **超過 3 個條件改列清單（STE List Rule）**：規則或共用條件超過 3 條時，改用 `<ul><li>` 條列，不要用 `<br>` 或一段長文硬塞五六條規則。

改寫範圍涵蓋所有看得見與讀得到的文字：標題、正文、表格、圖說、SVG 的 `text`／`title`／`desc`、按鈕、導覽、連結文字、`aria-label`、`alt`、分頁標題，以及由 JavaScript／`data-title` 產生的文字。排進 HTML 後只要有新寫或改過的字，就要再過一次同樣的關卡，並核對受影響的圖表與條件。做完 `asd-ste100` 修訂後，回頭對照原始規格與保護清單，確認數值、否定、前提、例外與不確定語氣（如「可能」「待確認」）都沒有被改丟。禁詞計數只能當輔助檢查，不能代替真正的改寫與語意核對。這裡只借用英文 STE 的結構原則，不套英文單字數上限，也不宣稱通過 STE 認證。

完成條件：草稿跑完兩階段改寫，確認零全形分號、零「地址」混用、無自創目標代號、無 AI 交差套話，才准進入下一節轉成 HTML。

## 6. 產出 HTML 計畫書

產出前必讀 [HTML 輸出規範](references/html-output.md)，把通過第 5 節改寫的定稿填入 [HTML 範本](assets/verification-plan-template.html)。範本沿用 `NOR_Flash_DV_Guide_V6.html` 的深色版面、章節導覽、流程卡片、SVG 圖塊與測項表骨架，只借版型，不帶入舊案例的產品數值或實測結論。

預設交付一個直接點開就能離線閱讀的單檔 HTML，用內嵌 HTML／SVG 畫出狀態圖、區域圖與各 Flow 流程圖，不產生 Mermaid 語法也不依賴外部套件。多項功能時用上方章節切換，單一功能時不要硬拆多章。

一般計畫保持設備中立，指定 Writer 時寫明第 1 節的使用條件。計畫裡只交代要記錄哪些讀值與怎麼判讀，不寫 Writer log 教學、C 程式碼、程式交接指令或任何「已編譯」字眼。

這份 HTML 是給工程師審查用的驗證計畫，不是已經測過的報告。還沒有實測資料時，狀態一律標「待審查／未執行」，絕不假造 PASS 統計、樣品編號或 Designer 確認結果。

完成條件：HTML 已寫出，圖表與測項完全一致、連結可點，沒有殘留 `{{...}}` 佔位符、範本提示或全形分號。

## 7. 審查、更新與交付

- 照檢查表自查後，實際開瀏覽器測過桌面版、窄螢幕、章節切換、錨點往返跳轉、關閉 JavaScript 閱讀與列印預覽。環境無法開瀏覽器時，完成靜態結構檢查並老實告知尚未做視覺檢查。
- 跑靜態文字檢查：確認產出 HTML 裡全形分號數量為 `0`、中國大陸用語「地址」數量為 `0`、沒有重複的「AI 推演，依」印章。
- 新計畫存成新檔案。使用者要求改既有計畫時，保留沒動到的其他章節，若檔案不在 Git 版控內要先備份。
- 回填實測結果時，把「原始預期／可能結果」「實測結果」「判定與依據」分欄保留，不要拿實測值蓋掉原本的預期。記下料號、測試條件與版本，單顆樣品的表現不直接外推到其他料號，並同步更新首頁與各章的已測／未測範圍。
- 實測沒重現推演出的異常時，回頭檢討模型假設、觸發窗口、測試條件與觀察手段，不要馬上斷言模型寫錯或晶片一定沒問題。
- 最終回覆附上 HTML 完整路徑，簡述涵蓋範圍、重要待確認事項、實測狀態，以及**本次套用 `speak-human-tw` 與 `asd-ste100` 的真實改寫對照摘要（列出實際發生的修改，最多 5 處，不足時如實寫出實際數量，絕不為了湊數故意把原句改壞：「原初稿寫法 → 違反規則 → 改寫後定稿」）**，讓工程師一眼確認已完成第二輪文字修飾才輸出 HTML。只要求計畫時交付到此結束。使用者已要求接續寫 Writer 程式時，完成計畫後再呼叫 `writer_program_flow_design`，沿用已確認範圍，不重新擴張測項。

- **speak-human-tw**：負責把繁體中文寫得自然清楚，並校準台灣用語。來源：https://github.com/Raymondhou0917/speak-human-tw
- **asd-ste100**：負責把操作步驟拆短、固定詞義與消除句構歧義。來源：https://github.com/danyuchn/asd-ste100-skill

### 如何編輯計畫書（Draft → Rewrite → HTML 三階段）

1. **第一階段（Draft 初稿）**：先把規格規則與測試邏輯寫成草稿，圈出不能改壞的保護清單：料號、文件版本、章節／頁碼、數值、單位、位址、pattern、指令與 opcode、暫存器與位元名稱、測項編號、規則編號、判定代碼、來源網址與引述原文。Program、Erase、Read、Reset 等工程名詞保持統一。程式碼、log、HTML 標籤、`id` 與連結目標不做語言改寫。
2. **第二階段（Rewrite 改寫 — 採 `speak-human-tw` 自動化事後摘要模式）**：
   - 套用 `speak-human-tw` 的「辦公文書／報告」情境：砍掉空話、刪掉對 Prompt 交差的自白句、拿掉每個測項開頭重複的「AI 推演，依 R…」印章、換掉中國大陸用語（如「地址」改「位址」）並統一全形標點。不自己編故事、加情緒或塞入原文沒有的結論。
   - 套用 `asd-ste100` 的結構規則：
     - **禁用全形分號**（Rule 8.1），全部拆成句號短句或 `<ul><li>` 清單。
     - **固定工程名稱與位址寫法**，直接寫出確切十六進位範圍與條件，不自創目標代號。
     - **一句一動作、主動祈使句、補齊動詞**，不寫漏動詞的電報殘句，並把禁止事項與前提放到動作前面。
     - **把名詞化贅詞改回動詞**（Rule 3.7），例如「進行…之驗證」改寫成「驗證…」，「完成…之確認」改寫成「確認…」。
3. **保留不確定性與判定條件（Keep Modality）**：前提、例外、先後順序、否定、適用範圍與不確定語氣（「可能」「推測」「待確認」「未實測」）都要原樣守住，不能為了把句子變短就刪掉判定條件，或把推測寫成鐵板釘釘的事實。
4. **第三階段（HTML 轉換與保真回讀）**：把改寫定稿填進 HTML 範本，逐項回頭核對原始規格與初稿，確認沒有漏掉或偷加事實，同時檢查 SVG 圖中文字、測項表與判讀說明完全一致，且整份 HTML 零全形分號。
5. **規則衝突優先順序**：第一優先守住事實、工程精確度與證據狀態，第二是本 skill 的測試設計與 HTML 結構，第三才是 `speak-human-tw` 的語感與 `asd-ste100` 的句型。寫清楚永遠比硬縮字數重要。
6. **參考依據與事後摘要**：保留真實從初稿改到定稿的紀錄，不虛構原句或故意寫錯再改。在計畫書的「參考依據」列出實際讀取的兩份 skill 網址與版本／讀取日期，標為「文字編輯參考」，不跟產品規格混在一起。最終回覆附上「原初稿寫法 → 違反規則 → 改寫後定稿」摘要表，證明真的跑完雙技能改寫才產出 HTML。
