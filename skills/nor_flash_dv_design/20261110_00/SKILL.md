# NOR Flash DV Design

本 skill 把「產品應該怎麼運作」畫成狀態圖。使用者用狀態圖確認 agent 理解的功能是否正確。接著 agent 沿狀態圖找反例，再產出可執行、可追溯的測試流程。

方法來源：pstack `/statechart`（https://github.com/cursor/plugins/tree/main/pstack/skills/statechart）。

## 啟動規則

本節規則在 skill 啟動時生效，優先於後文各步驟的執行順序。

### 提問規則

本 skill 只在需要 Datasheet 或其他必要文件時，才停下來問使用者。使用者可以選擇不提供。依下列順序處理：

1. 停止所有分析、推演與寫檔動作。
2. 收集本次所有缺少的文件與資料。不可一次只問一題。
3. 用條列式一次問完。每題一個項目，寫出需要的資料，以及可接受的給法（檔案路徑、頁碼、貼上文字）。
4. 使用者已在請求或先前回覆中提供的資料，不再問。
5. 收到全部回答後，才繼續。回答不完整時，只針對缺漏的項目再問一次，並繼續等待。
6. 使用者選擇不提供時，不再追問，依下列規則處理：
   - Datasheet 定義：依第 0 步第 6 項處理。
   - 其他文件：該項標「未取得」，相關規則標「待確認」。
   - 驗證目的：停止，不分析。
   - 現有測項：視為全新設計，繼續。
   - 操作限制：標「假設：無限制」，繼續。
7. 其他需要使用者核可的內容，不中途停下來問。這些內容包括「假設」與刻意設計的判斷。標示後，列入報告的「待確認清單」。第 0 步與第 1 步的兩個確認點不變。

必要問題至少包含下列項目：

- **Datasheet 索引**：
  - Datasheet 檔案路徑與版本。
  - 本功能所在的章節與頁碼。
  - 指令表所在的章節與頁碼。
  - 暫存器與狀態位元表所在的章節與頁碼。
  - 時序參數表所在的章節與頁碼。
  - 限制條件所在的章節與頁碼。
- **驗證目的**。
- **現有測項**。
- **操作限制**。

### 寫作規則

本 skill 的所有文字輸出，用下列兩個 skill 修飾：

- `speak-human-tw`：主要的修飾 skill。修飾整個說明流程的句子與語感。
- `asd-ste100`：輔助的修飾 skill。修飾句子結構，讓句子只有一種讀法。

輸出包含：提問文字、功能摘要、狀態圖說明、規則清單、測項、報告、最終回覆。

1. 開始撰寫任何輸出前，先載入 skill `speak-human-tw`，再載入 skill `asd-ste100`。兩者都要遵守。
2. 使用者沒有安裝這兩個 skill 時，依下列順序處理：
   1. 用條列式問使用者一次。寫出：要安裝哪個 skill、來源網址、安裝位置。使用者同意後，才安裝。
   2. 來源網址：
      - `speak-human-tw`：https://github.com/Raymondhou0917/speak-human-tw 。取得 `SKILL.md`、`references/patterns.md`、`references/taiwan-localization.md`、`references/protected-list.md`。
      - `asd-ste100`：https://github.com/danyuchn/asd-ste100-skill 。取得 `SKILL.md` 與 `references/writing-rules.md`。
   3. 先用上述網址取得。失敗時，才用 Web Search 找替代位置。只接受 owner 與 repo 名稱與 `Raymondhou0917/speak-human-tw` 或 `danyuchn/asd-ste100-skill` 相符的結果。不符合時，停下來問使用者，不自行採用。
   4. 安裝位置：與 `nor_flash_dv_design` 相同的上層資料夾，一個 skill 一個子資料夾。
   5. 只下載，不執行任何下載的腳本。要執行腳本，須先取得使用者同意。
   6. 使用者拒絕安裝時，只讀取內容，不寫入檔案，並繼續本次流程。
3. 取得失敗時，告知使用者，並繼續執行。只用本 skill 的「用詞」表與本節的句子規則，並在輸出開頭標「未套用 `speak-human-tw`／`asd-ste100`」。不可假裝已套用。
4. 套用 `speak-human-tw` 的方式：
   - 修飾對象是本 skill 自己產生的文字，不是使用者的稿件。
   - 情境選「辦公文書（報告）」。套用其去 AI 味、台灣用語、全形標點、保護清單與保真回讀的規則。
   - 不執行其「先列清單、等使用者確認」的兩輪流程。agent 在輸出前自行完成修飾。使用者在本次請求明確要求逐句確認時除外。
   - 不加入原文沒有的口語、故事、立場或第一人稱敘事。
   - 保護清單另外加入：Datasheet 數值、章節與頁碼、指令與 opcode、暫存器與位元名稱、`R*`／`F*`／`U*` 規則編號、測項編號、判定代碼、「用詞」表的用詞。
5. ASD-STE100 是英文標準。輸出為繁體中文時，套用其結構規則：
   - 一句只寫一個指令。
   - 句子保持簡短。
   - 使用主動語態。
   - 一個用詞只有一個意義。
   - 不改變原文的不確定程度。「推測」「假設」「待確認」維持原標示。
6. 程式碼、指令、暫存器名稱與錯誤訊息保持原文。
7. 修飾規則衝突時，依下列順序決定：
   1. 事實與標示：「推測」「假設」「待確認」「未核對原文」「未實機重現」。
   2. 「用詞」表與下文的判定代碼。
   3. `speak-human-tw`。
   4. `asd-ste100`。測項步驟與指令序列仍維持一句只寫一個指令。

## 基本原則

- 規格來自使用者提供的 Datasheet。只有使用者能判斷規格與狀態圖是否正確。
- 狀態圖是模型，不是晶片本身。模型與晶片、模型與測試程式之間可能不一致。
- 本 skill 預設用手工推演，不窮舉所有狀態。反例檢查表可減少遺漏，但不保證沒有遺漏。
- 只有使用者要求，且環境已安裝 TLC 與 Java 時，才用 TLA+／TLC 做模型檢查。
- 推演結果要用實測檢查。只有實測結果能證明反例真的存在。
- 本 skill 適用於任何功能。狀態、指令、資料 pattern、時序與預期值都從本次資料推導。
- 其他功能的審查結論，只有在本次資料也支持時才可沿用。
- 下文的 `〈〉` 是佔位符。套用時，換成本次功能的實際內容。
- 本 skill 不產生或修改測試程式。測試程式由使用者依測試流程更新。

## 用詞

本 skill 與其報告一律使用下列用詞。一個用詞只有一個意義。

| 用詞 | 意義 |
|---|---|
| 確認 | 使用者核可。agent 的動作不用此詞。 |
| 檢查 | agent 比對資料、文件或讀回值。 |
| 讀回 | 從晶片讀出資料或暫存器值。 |
| 測項 | 一個有判定的測試項目。 |
| 流程 | 依順序執行的一組測項。全稱為「測試流程」。 |
| 前置狀態 | 測項開始前，晶片必須處於的狀態。 |
| 反例 | 設計失效，但測項仍判定通過的路徑。不是一般所說的 counterexample（違反規則的路徑）。 |
| 反驗 | 只破壞一個前提條件，預期晶片拒絕指令的測項。與「反例」不同。 |
| 驗證目的 | 使用者要驗證的新設計、新功能、規格變更或異常行為。「驗證」一詞只用在此處。 |
| 測項屬性 | 正驗、反驗、邊界、未定義用法，四選一。 |
| 依據類型 | 規格明訂、假設、待確認，三選一。 |
| 待確認清單 | 報告中列出「假設」與「待確認」項目的清單。由使用者事後確認。 |
| 要問 Designer | `RECORD` 測項附帶的一個問句。使用者拿這句話去問 Designer，請 Designer 判定讀回值是否為設計本意。 |

## 0. 收集輸入

先向使用者收集下列資料。取得資料後，才開始分析。使用者選擇不提供時，依提問規則第 6 項處理。

1. 依「啟動規則」的提問規則，一次問完下列項目。使用者已在請求中提供的項目，不再問。
   - **驗證目的**：要驗證的新設計、新功能、規格變更或異常行為。
   - **Datasheet 定義**：功能描述、指令格式、狀態位元、保護位元、時序參數、限制條件。使用者可給檔案路徑，也可貼上文字。同時詢問 Datasheet 索引（章節與頁碼）。
   - **現有測項**：要審查的流程文件。全新設計可留空。
   - **操作限制**：治具能力、不可執行的操作、已知問題、刻意保留的規則。
2. 工作區中的測項、導讀與程式只代表現有流程。不可把它們當作規格。
3. 讀完 Datasheet 定義後，寫一段功能摘要。摘要寫出：功能做什麼、使用哪些指令與位元、前提條件、限制。
   - 讀 Datasheet 時，只讀使用者指定的索引頁，不讀整份 PDF。讀取工具依環境選用。
   - 表格或圖形無法萃取成文字時，請使用者貼上該頁文字。不猜內容。
4. 摘要中每一句都標來源，格式為「§章節 p.頁碼」。找不到來源的句子，標「推測」。
5. 請使用者確認功能摘要。使用者確認後，才進入第 1 步。
6. 使用者無法提供 Datasheet 定義時，執行下列動作：
   1. 只審查現有流程的結構問題，例如反例檢查表與連鎖依賴。
   2. 所有行為規則標「待確認」。
   3. 在報告開頭寫「未取得 Datasheet 定義」。
7. 在報告開頭寫出每份資料的角色：
   - **原始規格**：Datasheet 條文。只拿到二手引用的章節號時，標「未核對原文」。
   - **依據來源**：測試程式依據的文件。流程邏輯以此文件為準。
   - **說明文件**：給人閱讀的介紹或導讀。修改時，說明文件跟隨依據來源。
8. 列出使用者刻意保留的規則，例如固定等待時間、固定 pattern、固定位址。
9. 無法判斷某條規則是刻意設計或缺陷時，不列為缺陷，並列入待確認清單。刻意保留的規則不列為缺陷。報告只寫出此規則遮蔽了哪些行為。

完成條件：使用者已確認功能摘要。報告開頭已寫出驗證目的、原始規格、依據來源與刻意保留的規則。

## 選定狀態維度

依驗證目的，從下表選出會影響判定的維度。只保留相關的維度。在報告的「模型未涵蓋」段落寫出捨去的維度。

| 維度 | 常見內容 | 可觀察方式 |
|---|---|---|
| 陣列資料 | 目標區、鄰近區、同 Sector／Block 其他區 | 讀取指令讀回比對 |
| 暫存或揮發性狀態 | 內部暫存區、揮發性設定、模式旗標 | 對應的讀取指令 |
| 狀態暫存器 | BUSY、WEL、Suspend、錯誤旗標、保護位元 | Read Status Register 類指令 |
| 保護設定 | 範圍保護、個別區塊保護、密碼／OTP／鎖定 | 保護暫存器讀回＋實際寫入或抹除結果 |
| 進行中的操作 | Program、Erase、Suspend、Resume | BUSY 輪詢、時間量測 |
| 非揮發性設定 | 非揮發性狀態位元、OTP、非揮發性保護 | 斷電重啟後讀回 |
| 電源與時序 | 上電、斷電、Reset、電壓、等待時間 | 治具控制與量測 |
| 介面模式 | 位址位元數、I/O 模式、Dummy cycle | 設定讀回＋實際通訊結果 |

## 1. 畫出產品應該怎麼運作

1. 用 Mermaid `stateDiagram-v2` 畫出與驗證目的相關的狀態。
2. 狀態名稱寫可觀察的內容，格式為「〈目標區〉=〈資料〉／〈狀態位元〉=〈值〉」。不寫程式變數名稱。
3. 箭頭寫觸發指令與條件，格式為「〈指令序列〉[〈條件〉]」。
4. 也畫出負向切換。例如：條件不成立時，晶片忽略指令，狀態不變。
5. 每張狀態圖保持約 20 條箭頭以內。箭頭太多時，執行下列其中一項：
   - 把行為相同的狀態合併為一個較粗的狀態。
   - 依功能階段拆成多張狀態圖。

   不可合併違反不同規則的狀態。反例路徑上的每個狀態都要保留。
6. 把每條路徑整理成表。欄位為：初始資料、致能與保護狀態、執行指令、預期讀回值、依據條文、依據類型。
7. 列出規則並編號：
   - `R*`：必須成立的行為。
   - `F*`：不允許發生的狀態或切換。
   - `U*`：規格未定義的行為。寫出缺少的資料，例如條文、時序參數或治具規格。
8. 每條規則標一個依據類型。

完成條件：狀態圖中每個狀態與每條箭頭都對應至少一條規則。每條規則都有依據類型。

**在此停止。** 請使用者確認狀態圖與規則清單符合驗證目的。使用者確認後，才進入下一節。

## 測項分類：正驗、反驗、邊界、未定義用法

每個測項標一個測項屬性：正驗、反驗、邊界或未定義用法。四類都要產生測項。某一類沒有測項時，在報告寫出原因。

### 正驗

每條 `R*` 至少一個測項。測項在規格允許的條件下執行。預期值來自規格明訂。

### 反驗

1. 列出每條 `R*` 的前提條件。常見的前提條件有：致能位元、保護狀態、位址合法、長度合法、指令順序、模式設定、晶片不在忙碌狀態。
2. 每個反驗測項只破壞一個前提條件。其他前提條件保持合法。
3. 預期結果為：晶片拒絕指令，狀態不變。
4. 規格沒有寫出拒絕後的行為時，此預期標「假設」，並列入待確認清單。例如：規格沒寫是否設定錯誤旗標。
5. 每條 `F*` 也至少一個反驗測項。

### 邊界

逐項判斷下列邊界是否適用。每個適用的邊界測兩個點：剛好在邊界上，以及超出邊界一格。

- 位址：功能區第一個位址、功能區最後一個位址、晶片最後位址、位址位元數切換處。
- 長度：0、1、最大值、最大值加 1。
- 區塊：跨 Page、跨 Sector、跨 Block、跨保護範圍邊緣。
- 時序：規格最短與最長等待時間、操作剛開始時中斷、操作即將結束時中斷。使用者刻意固定的等待時間不列入。
- 次數：重複執行、連續 Suspend、巢狀 Suspend、累計上限。
- 電源：電壓上限、電壓下限、上電斜率。治具無法控制的項目標「不適用」，並寫出原因。

### 未定義用法

主動設計 Datasheet 沒有定義的操作。逐項判斷下列操作是否適用：

- 晶片忙碌時送出其他指令，包含本功能指令、讀取、寫入與設定類指令。
- 在指令、位址或資料的中途拉高 `/CS`。
- 送出不是 8 的倍數的時脈數。
- 使用未定義的指令順序或指令組合。
- 重複送出同一個指令。
- 少送或多送 dummy 或資料。
- 本功能與其他功能同時作用，例如保護、Suspend、Reset、不同位址模式、不同 I/O 模式。
- 中斷或 Reset 後立刻送出指令。

判定分兩層：

- **安全性**：判 `PASS` 或 `FAIL`。安全的條件為：晶片沒有停止回應、通訊可以恢復、未操作區域的資料與設定不變。安全性預期屬於「假設」，並列入待確認清單。
- **功能結果**：判 `RECORD`。讀回值是否正確，由 Designer 決定。`RECORD` 不計入 PASS／FAIL。

每個 `RECORD` 測項寫出下列三項，讓使用者事先知道會看到什麼、看到後要問什麼：

1. **可能結果**：列出 2～3 種可分辨的結果，每種寫出對應的讀回值。例如：「Buffer 仍是 C3h x256（保留）」或「Buffer 全部 FFh（清除）」。
2. **觀察點**：哪一個讀回值決定是哪一種結果。
3. **要問 Designer**：一個問句。問句寫出具體的指令與讀回值，問 Designer 兩件事：這是不是設計本意？可不可以寫成規格？例如：「8Ah 完成後，Buffer 仍保留 C3h x256。這是設計本意嗎？可以寫成規格嗎？」

實測後，預期欄改寫成「實測結果（料號）：〈讀回值〉」，問句保留。結果只代表該料號；其他料號結果不同時，仍判 `RECORD`，一樣要問 Designer。

每個「要問 Designer」問句都列入待確認清單。

未定義用法可能讓樣品進入未知狀態。依序執行下列規則：

1. 把這類測項放在流程最後，或獨立執行。
2. 測項結束後，執行 Power Cycle，再重新初始化樣品。
3. 讀回檢查樣品已回到已知狀態。
4. 每個未定義用法測項各執行一次 Power Cycle，不合併。報告寫出 Power Cycle 的總次數。

完成條件：每條 `R*` 都有正驗與反驗測項。邊界清單與未定義用法清單的每一項都有「適用」或「不適用」結論。

## 2. 沿狀態圖找反例

從同一個起始狀態推演下列路徑：正常路徑、邊界條件、操作順序變化、中斷與恢復。

每個反例寫成最短路徑：

`起始狀態 → 操作順序 → 可能結果 → 違反的規則 → 現有測項是否仍判定通過`

逐項套用下列反例檢查表。每一項寫出一個結論：命中、不適用或已涵蓋。

| 檢查 | 會出問題的測項設計 | 反例 |
|---|---|---|
| 初始值遮蔽 | 預期結果等於前置狀態。例如預期空白值，前置狀態也是空白值。 | 被測操作沒有作用，測項仍通過。 |
| 寫入語意 | 新資料與底資料的組合無法分辨覆寫、AND 與 OR。 | 寫入邏輯錯誤，結果仍相同。 |
| 位址忽略 | 目標固定在位址 0 或邊界對齊位址。鄰近區與目標區資料相同。 | 位址解碼錯誤或高位元被忽略，測項仍通過。 |
| 波及他區 | 只讀回目標區。 | 同 Sector、同 Block 或相鄰區被修改，測項沒有發現。 |
| 自我前置 | 被測指令也用來建立自己的前置狀態。 | 指令失效時，前置狀態與結果一起失效，彼此遮蔽。 |
| 觸發未證明 | 送出中斷、Reset 或 Suspend 前，沒有檢查目標操作正在進行。 | 目標操作已結束或沒有啟動，結果仍正常。 |
| 狀態位元 | 只等完成旗標。不檢查過程中與結束後的其他位元。 | 晶片沒有進入忙碌狀態，或致能位元沒有清除，測項沒有發現。 |
| 負向缺漏 | 只測合法條件：已致能、未保護、位址合法、長度合法。 | 條件不成立時，晶片仍執行指令。 |
| 結果無差異 | 操作前與操作後的預期狀態相同。 | 操作沒有執行，測項仍通過。 |
| 連鎖依賴 | 後一個測項依賴前一個測項的結果，且沒有前置狀態檢查。 | 前一個測項失敗時，後續測項連鎖誤判。 |
| 殘留設定 | 沒有讀回保護、模式或非揮發性設定就開始測試。 | 樣品殘留上一輪的設定，造成誤判。 |
| 治具條件 | 斷電、電壓與時序由治具決定。 | 治具沒有達到規格條件。 |

完成檢查表後，對本次功能的每條 `R*` 與 `F*` 回答一個問題：「哪個最小的設計錯誤會違反此規則，但現有測項仍判定通過？」

把每個現有測項對應到狀態圖，再分成兩類：

- **a. 未涵蓋**：沒有任何測項經過的重要狀態或切換。
- **b. 會誤判通過**：測項經過此路徑，但設計失效時仍判定通過。

每個反例標一個來源：「模型推演」或「實測重現」。只有推演時，寫「未實機重現」。

實測沒有重現反例時，先假設模型錯誤。回到第 1 步檢查狀態圖與規則。找到證據證明模型正確後，才可判定設計正常。

完成條件：檢查表每一項都有結論。每個現有測項都已歸類。

## 3. 轉成可執行的測試流程

1. 產出測項表與 Mermaid `flowchart TD` 流程圖：
   - 測項表是主要內容。欄位為：測項編號、測項屬性、規則編號、前置狀態、指令、觀察點、預期值、判定、要問 Designer。規格明訂的測項，「要問 Designer」欄填「不用問（規格明訂）」。
   - 流程圖只寫：測項編號、測項屬性、判定、執行順序。前置狀態檢查點與恢復步驟也畫在圖上。
2. 依下列原則設計測項：
   - 預期結果與前置狀態不同。需要時，先放入可辨識的資料或設定，再讀回檢查已生效。
   - 資料 pattern 能分辨覆寫、AND 與 OR。依本次功能的 bit 特性選擇 pattern。
   - 一般測項的目標位址不用 0，也不用單純的邊界值。邊界由「邊界」類測項測試。
   - 在鄰近區預先寫入不同的誘餌資料。
   - 測項會改變陣列或非揮發性設定時，事後讀回足夠的範圍，與已知影像比對。範圍要能發現波及。
   - 被測指令通過測項前，不用它恢復樣品。改用已通過測項或獨立的方法建立前置狀態。
   - 前置狀態相同的測項分在同一群，共用一次 Erase 與 Program 建立前置狀態。群內每個測項之間，仍依第 4 步第 6 項加入前置狀態檢查點。
   - 中斷類測項先讀回檢查目標操作正在進行，例如忙碌旗標為 1。檢查通過後，才送出中斷。沒有讀到忙碌旗標時，判 `INVALID`。
   - 規格未定義的觀察點判 `RECORD`。預期值欄寫「可能結果」，「要問 Designer」欄寫問句，寫法依「未定義用法」一節。
3. 使用下列判定代碼：

   | 代碼 | 意義 |
   |---|---|
   | `PASS` | 觀察點符合預期。 |
   | `FAIL` | 觀察點不符合預期。 |
   | `SETUP_FAIL` | 前置狀態檢查失敗。不計為樣品失敗。 |
   | `BLOCKED` | 依賴的前一個測項失敗。本測項沒有執行。 |
   | `INVALID` | 觸發條件沒有成立。本次結果不可用，要重測。 |
   | `RECORD` | 規格未定義。記錄讀回值，附「要問 Designer」問句。不計入 PASS／FAIL。 |

4. 每個反例寫出重現方式：要讀回或量測什麼、哪個結果表示設計正常、哪個結果表示缺陷發生。
5. 每個測項對應第 1 步的一條規則或一條切換。規格不足以判定時，標「待確認」，並寫出缺少的資料。

完成條件：每條 `R*` 與 `F*` 至少有一個測項。每個反例都有可分辨設計正常與缺陷的判準。

## 4. 比較現有流程與改良流程

1. 列出可共用的部分，例如初始化、樣品設定、Baseline、量測。列出必須獨立執行的部分。每一項寫出原因。
2. 製作新舊對照表。欄位為：舊測項、新測項、變更原因。
3. 逐條檢查：原本測試的每條規則與每條關鍵路徑，在新流程中仍有測項。
4. 統計新舊流程中正驗、反驗、邊界、未定義用法各有幾個測項。
5. 寫出新流程省下與增加的步驟數與執行次數，例如 Erase、Program、讀回與 Power Cycle 的次數。同時寫出總測項數。新流程較長時，直接寫出，並說明增加的判別能力。
6. 前一個測項可能影響下一個測項時，在流程圖中加入兩個節點：恢復步驟、前置狀態檢查點。檢查不符時判 `SETUP_FAIL`，並執行復原流程。
7. 無法可靠恢復的測項，保留獨立執行。

完成條件：對照表包含所有舊測項。每條原有規則都有對應測項。

## 5. 實測回填

使用者貼上實測 log 或讀回值時，進入本步。不重做全部流程。

1. 對照 log 與第 3 步的測項表，逐項更新判定。
2. 依結果，把每個反例的來源改為「實測重現」或「未重現」。
3. 反例「未重現」時，依第 2 步的規則處理：先假設模型錯誤，回到第 1 步檢查狀態圖與規則。
4. 修改狀態圖或規則時，列出改動的 `R*`、`F*`、`U*`，並請使用者確認。
5. `RECORD` 測項的預期值欄改寫成「實測結果（料號）：〈讀回值〉」，問句保留。實測值落在「可能結果」之外時，問句改寫成問這個實測值。
6. 更新報告的判定、反例來源與待確認清單。只修改受影響的段落。

完成條件：每個有 log 的測項都已更新判定。每個 `RECORD` 測項都有實測值與問句。每個受影響的反例都已更新來源。

## 報告結構

報告依下列順序排列：

1. **摘要**（一頁以內）：關鍵規則、會誤判通過的測項、主要反例、待確認清單。待確認清單另列一張「要問 Designer」表，欄位為：測項編號、可能結果或實測結果、問句。
2. **推演方式聲明**：寫「本次為手工推演，未窮舉狀態空間。」已執行 TLC 時，改寫實際執行的檢查範圍。
3. 第 0 步到第 4 步的內容。
4. **模型未涵蓋**：列出下列項目。
   - 捨去的狀態維度。
   - 沒有畫進狀態圖的功能交疊、時序與電源情境。
   - 現有測試程式與狀態圖不一致的地方。

## 產出與修改

- 預設把報告寫成新的 Markdown 檔。檔案放在使用者指定的位置，或放在依據來源旁邊。不修改使用者的既有檔案。
- 使用者要求套用建議時，依序執行：
  1. 檔案不在版本控制中時，先建立 `.bak_YYYYMMDD` 備份。
  2. 先修改依據來源，再修改說明文件。
  3. 讓兩份文件的步驟編號、指令與預期值一致。
  4. 在依據來源加入「與舊版步驟對照」表。
  5. 提醒使用者：測試程式要依新流程更新。
  6. 修改說明文件時，保留既有版面與其他章節。只修改相關段落。
  7. 修改 HTML 後，檢查標籤是否成對。
- Mermaid 規則：
  - 節點文字用 `<br/>` 換行。
  - 文字含括號、冒號或引號時，用雙引號包住節點文字。
  - 待確認的節點用醒目顏色的 `classDef` 標示。
- 最終回覆寫出：產出檔案、主要反例、待確認清單、「要問 Designer」問句、只經推演而尚未實測的內容。
