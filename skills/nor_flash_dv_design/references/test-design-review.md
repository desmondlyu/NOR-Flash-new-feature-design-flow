# 測試設計檢查

設計每個功能時逐項檢查。內部記下「已涵蓋／不適用／待補」，正文只呈現有意義的理由與缺口，不把整張檢查表變成使用者問卷。

## 讓推演可被審查

- 產品行為圖與測試順序圖用途不同：前者呈現晶片狀態如何隨指令與條件變化，後者呈現工程師如何測試。不能用後者取代前者。
- 每條重要異常路徑列出初始狀態、必要操作、可能異常、違反規則及對應測項。以足以說明問題的短路徑呈現，不宣稱是經工具求得的最短路徑。
- 「產品違反規則」與「測項未能發現錯誤」分開說明。正常條件與讀回設計應足以分辨兩者。
- 未定義行為列待確認；未實測路徑標推演。未找到反例不等同證明沒有缺陷。
- 明列假設、未涵蓋狀態／條件及影響。圖形簡化不得隱藏重要分支或不同規則的違反位置。

## 讓錯誤能被看見

- 初始值遮蔽：操作前與預期結果相同時，即使指令沒執行也可能通過。正驗先建立不同資料；反驗先證明相同操作在合法條件下能成功。
- 寫入語意：pattern 是否能分辨本功能的覆寫、AND 或其他規格行為？不要將其他功能的寫入語意套進來。
- 位址忽略：依容量選擇能區分位址位元的測試點；不要只測位址 0 或單一對齊點。單一非零位址不代表已涵蓋全部位址解碼。
- 波及他區：目標與鄰近區使用可區分資料。操作後讀回適當範圍；整組操作結束後再檢查先前受保護區，避免晚發生的破壞被漏掉。
- 自我前置：不要讓待測功能同時建立自身唯一判定依據。優先採獨立方式；沒有獨立方式時揭露依賴與限制。
- 狀態觀察：資料、狀態位元與時間各依規格判讀。不把所有功能簡化成只看資料或只看 BUSY。
- 觸發有效性：中斷、Reset、Suspend 等操作要能證明發生在要求的窗口；未觸發則結果無效。中斷後應有的狀態依該指令定義，不通用要求 BUSY 仍為 1。
- 連鎖依賴：共用前置資料後，每個可能改變狀態的步驟都要檢查下一步的前提。無法可靠共用就獨立初始化。
- 殘留設定：先讀取會影響測試的保護、模式、非揮發性設定。復原明列目標是起測值還是指定結束值。

## 覆蓋相關情境

以下為候選檢查角度，依主 skill 的用途與 Writer 使用條件篩選，不逐項強制展開。優先常見應用、常見誤用及重要資料完整性問題；等效情境合併。Writer 固定低頻，以 Software Reset 處理可支援的初始化／復原，不加入 SPEED、上下電、/HOLD 或特殊電源控制。明確排除者簡述「本次範圍外」，不當成待補設備清單；已納入範圍但無法執行者才標未執行。Software Reset 不代表已驗證斷電行為。

- 正常／禁止條件：致能、保護、合法位址、資料長度、模式、忙碌狀態、指令順序。反驗每次只改一項條件，結果依條文。
- 邊界：區域首尾、Page／Sector／Block 跨界、容量與位址模式切換、最短／最長時間、重複次數。時間點要考慮量測解析度，不編造精確觸發能力。
- 功能交互作用：依本次功能與用途選擇 Reset、Suspend／Resume、保護及介面模式；Power Cycle 僅在非 Writer 的適用範圍或使用者明確擴充時考慮。
- 未定義用法：依適用性考慮忙碌中送指令、中途拉高 /CS、不完整時脈、少送／多送資料或 dummy、未定義序列。標示操作風險及復原方法。
- 電壓、溫度、時脈：若與目的相關，依規格提出測試條件。設備能力未知標待確認；設備做不到標「適用但未執行」，不能標成不適用。
- 刻意配置：使用者指定的固定等待、位址、pattern 應保留並說明會遮蔽哪些行為，不自動改掉或判為缺陷。

## 結果與證據

計畫以「預期與判定方式」為核心，實測前不填通過結果。若需要結果名稱，可用：

- PASS／FAIL：有已確認規格或工程要求作依據的符合／不符合。
- 前置失敗：測試起始條件未成立，不等同產品功能失敗。
- 結果無效／需重測：必要觸發未成立。
- 未執行：未做或因相依條件被阻擋，寫明原因。
- 待確認：規格未定義或依據不足，只記錄觀察，不算正式 PASS／FAIL。

未定義測項列出可分辨的可能結果、關鍵讀回值與一個具體問題，例如「送出〈指令〉後讀到〈值〉，這是設計本意嗎？可以納入規格嗎？」可能結果不是完整窮舉，落在清單外也不能直接判產品 FAIL。

規格未定義的恢復性、鄰區完整性等期待仍屬工程觀察；經確認為工程要求後才能依該要求判定。文件應區分功能結果、執行完整性與待確認項目，未執行或結果無效不可算成全部通過。

## 新舊流程與實測

只有提供舊流程才做對照：每個舊測項要有保留、合併、替換或移除的理由，檢查原有重要覆蓋仍存在。新功能不產生虛構舊流程。

推演發現的問題寫成「可能漏掉的錯誤」，標未實測。實測資料須保留產品、條件與來源；變更預期必須新增依據，不能只為符合觀察而放寬判定。
