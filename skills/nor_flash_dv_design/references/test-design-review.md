# 測試設計檢查

設計每個功能時，先照主 skill 第 1 節篩選。內部把情境分成「已選／合併／補充候選／範圍外」，正文只留下關鍵取捨與缺口。這份清單用來檢查「已選測項抓不抓得到錯」，不是叫你逐條硬湊新測項。

## 入選檢查

- 分清楚「產品功能驗證」「指定探索」「CP 量產篩選」三種用途，使用者指定的目的與條件全部保留。
- 每個情境都有實際用途或應用依據，否則明標「AI 推演」或「使用者指定探索」。規格允許的操作不自動等於客戶常用操作。
- 每一項都說得清楚要抓什麼錯、為什麼其他測項不能取代。等效條件合併，排下去沒有新判別價值就停。
- 只有已選測項展開完整步驟。補充候選只寫新增價值與納入條件，不畫 Flow。
- 不用測試時數、成本或固定測項數上限刪減必要驗證。
- CP 建議寫明攔截目的、判定依據，以及屬於實測／失效案例支持還是待驗證假設。沒證據只列候選，DV 通過不等於 CP 攔截有效，未定義行為在確認前不得正式判 FAIL。

## 讓推演可被審查

- 「產品狀態行為圖」跟「測試執行順序圖」是兩件事：前者畫晶片狀態怎麼隨指令與條件改變，後者畫工程師怎麼跑測試，不能拿後者頂替前者。
- 每條關鍵異常路徑都寫出「初始狀態 → 必要操作 → 可能異常 → 違反規則 → 對應測項」，用夠看懂問題的短路徑呈現，不宣稱是用形式驗證工具算出來的最短路徑。
- 把「晶片真的違反規則」跟「測項設計不良沒抓到錯」分開講，正常對照與讀回設計要能分辨這兩件事。
- 規格未定義的行為標「待確認」，還沒上機跑過的路徑標「推演」。沒找到反例不等於證明晶片沒有缺陷。
- 寫清楚本次採用的假設、沒涵蓋到的狀態／條件與影響。就算為了好讀簡化圖形，也不能把會影響判斷的重要分支藏起來。

## 讓錯誤能被看見

- **初始值遮蔽**：操作前的資料如果跟預期結果一模一樣，就算指令根本沒動也會看起來像 PASS。正驗要先鋪不同的底圖資料，反驗要先證明同一道操作在合法條件下真的會成功。
- **寫入語意**：選的 pattern 能不能分出這個功能是覆寫、位元 AND，還是其他規格行為？不要把別的功能語意直接套進來。
- **位址忽略**：主陣列選址預設照主 skill 的固定基準區公式算出，禁止每次隨機挑號。單區功能邏輯預設取當前有效視窗的「中基準區」，並核對它是否非全零及鄰區是否合法，避免單測零位址遮蔽位址清零異常。需要空間代表性時，依判別價值選取頭、中、尾基準區。固定基準區與單位對齊起點不能代替完整的位址線解碼或跨界測試，若目標是檢查位址位元獨立性、別名問題或跨界行為，要依待測位元或邊界補上成對位址與可區分的資料，並在未涵蓋範圍老實寫清楚。
- **波及他區**：目標區跟鄰近對照區要放不同資料。做完先讀回鄰近範圍，整組流程跑完再回頭檢查先前受保護的區域，避免晚發生的干擾漏網。
- **自我前置**：不要讓待測的新指令同時去建立它自己唯一的判定基準。優先用獨立已知指令鋪底或讀回，真的沒有獨立方法時要寫明依賴與限制。
- **狀態觀察**：資料內容、狀態位元與完成時間各自照規格判讀，不要把所有功能都簡化成只看資料或只看 BUSY。
- **觸發有效性**：中斷、Reset、Suspend 等操作要能證明真的打在目標時間窗裡，沒打中就判「結果無效／需重測」。中斷後的狀態照該指令規格判讀，不一概要求 BUSY 繼續停在 1。
- **連鎖依賴**：共用前置底圖時，每做完一步可能改動狀態的操作，都要先確認下一步的前提還在。沒把握安全共用就各自獨立初始化。
- **殘留設定**：起測前先讀取會影響結果的保護位元、位址模式與非揮發性設定。復原階段寫清楚目標是回到起測原始值還是指定結束值。

## 覆蓋相關情境

下面只是挑測項時的檢查角度，照主 skill 的入選條件與預設機台範圍過濾，不用每條都展開。優先挑有實際依據的應用、使用者指定探索與具體資料損毀風險。預設排除高頻及外部 `/RESET`、`/HOLD`、`/WP` 腳位控制，優先用 Software Reset，真實上下電只列機台允許時的補充建議，Writer 沿用合法低頻設定。排除掉的簡述範圍外，選進來但機台做不到的就保留缺口，不偽造替代結果。

- **正常／禁止條件**：寫入致能、保護狀態、合法位址、資料長度、介面模式、忙碌狀態、指令先後順序。反驗每次只改一項條件，預期結果照條文寫。
- **邊界**：區域首尾、Page／Sector／Block 跨界、容量與位址模式切換、最短／最長時間、重複次數。時間窗口要顧及儀器量測解析度，不瞎編做不到的精準觸發。當保護分界、跨頁回繞、跨區段或跨 Die 交界不在頭、中、尾基準區時，照主 skill 例外規則直接挑實際交界兩側的單位，並寫明依據。
- **功能交互作用**：看有沒有新判別價值，挑選 Software Reset、Suspend／Resume、軟體保護與介面模式切換。Power Cycle 等確認機台能力並納入範圍後才展開。
- **未定義用法**：視情況考慮忙碌中送指令、中途拉高 `/CS`、時脈數不完整、少送或多送資料／dummy、未定義指令序列，並標示風險與復原方式。
- **電壓、溫度、時脈**：跟本次驗證目的有關時才依規格提出條件。機台能力不明標「待確認」，機台做不到標「適用但未執行」，不能硬寫成不適用。
- **刻意配置**：使用者指定的固定等待、固定位址或固定 pattern 一律保留，同時點出這樣設定可能會遮住哪些現象，不擅自改掉或判成錯。

## 結果與證據

驗證計畫的核心是「預期結果與怎麼判讀」，還沒實測前不填通過統計。需要標示判定分類時，統一用這五種：

| 分類 | 代表意思 |
| :-- | :-- |
| **PASS／FAIL** | 有明確規格或已確認工程要求當依據的符合／不符合 |
| **前置失敗** | 起測條件沒建立好（例如預檢沒過），不算產品功能失敗 |
| **結果無效／需重測** | 必要的觸發條件沒打中（例如沒落在指定時間窗） |
| **未執行** | 還沒測，或因前一步卡住沒往下跑，需寫明原因 |
| **待確認** | 規格沒定義或依據不足，只記錄觀察值，不算正式 PASS／FAIL |

未定義測項要寫出可分辨的幾種可能結果、關鍵讀回值，以及一句具體問 Designer 的話，例如：「送出〈指令〉後讀到〈數值〉，這是設計本意嗎？要不要寫進規格？」列出的可能結果不是窮舉，就算實測跑出清單外的反應，也不能直接判產品 FAIL。

規格沒明寫的恢復能力或鄰區零干擾期待，在 Designer 確認成正式工程要求之前都算工程觀察。計畫裡要把「功能判定結果」「執行完整度」「待確認觀察」分開算，不能把未執行或結果無效混進全部通過。

## 新舊流程與實測

只有使用者提供舊流程時才做新舊對照，交代每個舊測項是保留、合併、替換還是移除，確認原本重要的覆蓋沒漏掉。全新功能不要自己編一份假舊流程來對比。

文件推演抓到的風險寫成「可能漏掉的錯誤」並標「未實測」。回填實測資料時保留料號、條件與來源，若要修改預期結果必須有新規格依據，不能只為了遷就手邊樣品的表現就放寬標準。

## 完整敘述與呈現檢查

- 逐項檢查：不用翻代號表，光看測項就能讀出確切位址、長度、資料與前置狀態，且指令、暫存器與位元都有解釋意義。
- 核對所有測試位址都能追溯到規格明訂、使用者指定、頭中尾固定基準算式或有寫明理由的例外配置，沒有隨意跳動的位址。確認有效視窗已取「實際容量 × 選擇器可達範圍 × 獲授權範圍」的交集、容量用 bytes 換算、區域配置單位與頁長對齊、多單位操作沒越界也沒跟鄰區撞車（有重疊或無鄰區已老實揭露）、邏輯位址與實際傳輸位址位數（6 位或 8 位十六進位及 Bank／Die 狀態）一致，並分開標明操作影響範圍與讀回觀察範圍。
- 正文與圖說都改用完整時間意義，典型值、最大值與工程設定分開標示，未知位址或超時上限列待確認。
- 每個納入計畫的 Flow 都有專屬流程示意圖，且與產品狀態圖分工清楚。逐張圖對照表格的條件、位址與判斷分支。
- 總覽、Flow 圖、測項表列與返回連結都能雙向點選跳轉，支援跨章切換、鍵盤焦點、關 JavaScript 閱讀與列印對照。
- 全部看得見與輔助閱讀的文字都跑過雙技能改寫，排進 HTML 後改過的字也重新檢查過，真實改寫紀錄與保護清單核對無誤。必讀參考檔缺漏時停在文字草稿。
